This threat model covers the M0 foundation plus the M1 People-scope slices: synthetic tenants, local PostgreSQL, a minimal API plus the Postgres outbox claim helpers and worker loop, and a React 19 + Vite shell with sign-in, sign-out and a People directory screen fed by `GET /v1/people`, where a member who can write People can add and edit core identity fields in an inline panel. The outbox has no producer, no deployed consumer and no production handler. The shell has no delete, restore, status change, placement change, user linking, import or export UI, no invitation UI and no screen for any other module. Three rows are not M0: T36 records the M1 people-scope database half added by `suite/db/migrations/0012_people_scope.sql`, T37 records the owner-only scope authoring path added on top of it, and T38 records the member-facing directory write path, because the controls and residuals of all three belong next to the tenancy rows they modify. It has not been reviewed or approved by a named human security owner, and no independent penetration test has been performed. M0 is not production-ready. Do not load real customer, payroll, bank, statutory-identifier or design-partner data into this build. The design-partner gate in [`../security.md`](../security.md) remains unticked.

The baseline controls and target controls are in [`../security.md`](../security.md); schema and privilege conventions are in [`../../db/README.md`](../../db/README.md); tenancy and migration decisions are recorded in [`../adr/0002-postgres-rls-tenancy.md`](../adr/0002-postgres-rls-tenancy.md), [`../adr/0003-migration-staging-and-promotion.md`](../adr/0003-migration-staging-and-promotion.md), [`../adr/0005-modules-and-entitlements.md`](../adr/0005-modules-and-entitlements.md) and, for the scope layer, [`../adr/0007-people-scope.md`](../adr/0007-people-scope.md).

## 1. Assets

- Tenant business data: people, employment, projects, entitlements and audit events.
- The scope map: `membership_scope` rows, the `person.user_id` link and the org-unit tree, which together decide how far a member's visibility stops inside its own tenant.
- Identity data: `app_user` password hashes, memberships, invitations and opaque session tokens.
- The People directory CSV: seven identity fields per non-deleted person in the session tenant. The same seven fields per row are what the directory screen shows and, for six of them, what a member with `people.write` can now create and edit.
- The audit trail: provisioning, entitlement changes, authenticated access denials, People exports, the owner-only person/user links and membership scope changes, and the member-written `person.created` / `person.updated` rows.
- Database and CI credentials: `saas_owner`, `saas_runtime`, `saas_auth`, `saas_worker`, database URLs and CI-only dummy credentials.
- The outbox queue itself: event type, aggregate id and `payload` contents, which are readable by whoever holds a claim for that tenant.
- Browser session state: the HttpOnly `saas_session` cookie, the in-memory CSRF token used for sign-out and for every person write, and the rendered module/role metadata.
- Availability of the API, database, export path and web shell.
- Repository integrity: migrations, grants, workflow, lockfile and pinned frontend dependencies.

## 2. Actors

- Tenant member with a role: owner, admin, HR, finance, manager, employee or auditor. From 0012 a member also carries a scope — the whole tenant, one legal entity, one org unit and its subtree, or (for `employee`) only their own person record — which can only reduce what the role allows (T36).
- Tenant administrator acting through the owner-only CLIs.
- Platform operator with `saas_owner` or superuser access.
- Unauthenticated internet client or credential-stuffing attacker.
- Malicious or compromised dependency, GitHub Action or CI runner.
- Insider with repository or database access.

## 3. Trust boundaries and data flows

1. **Browser → API.** The M0 React/Vite shell presents an opaque `saas_session` cookie from sign-in. State-changing requests require an exact `Origin`; logout, `POST /v1/people` and `PATCH /v1/people/:id` also require the CSRF token returned in the session response and held only in module memory. The browser never receives the session token, and credentials are not placed in the URL or browser storage.
2. **API → PostgreSQL as `saas_runtime`.** Each protected request opens a member transaction, sets `app.tenant_id` and `app.user_id` transaction-locally, resolves the membership role, checks platform access, entitlement and role permission, then runs explicit SQL under RLS. From 0012 the same `app.user_id` feeds the restrictive `scope_*` policies on `person` and `employment`, so the row set is narrowed by legal entity, org-unit subtree or the person/user self link before any service code runs (T36). The runtime role is not the table owner, has no `BYPASSRLS`, no DDL and only the reviewed grants.
3. **API → PostgreSQL as `saas_auth`.** Login, session lookup, membership status and invitation acceptance use narrow identity grants and security-definer functions before a tenant transaction exists. `auth_session` and `invitation` carry `tenant_id` but deliberately have no RLS; the runtime role cannot reach them.
4. **Operator CLI → PostgreSQL as `saas_owner`.** Provisioning, entitlement changes and invitation creation are owner-only paths, never API routes. They write audit rows in the same transaction.
5. **API → People CSV.** `GET /v1/people/export` uses two member transactions: a durable export audit row before the first byte, then a gateway-rechecked server-side cursor and streamed CSV. The response is not stored.
6. **API → person identity write.** `POST /v1/people` and `PATCH /v1/people/:id` each open one member transaction under the People write gate: session and CSRF first, then membership, platform access, entitlement and role, then body validation, then the 0012 `scope_insert` / `scope_update` policies. A create sends the six identity fields and nothing else — the person id and `tenant_id` come from the server, `tenant_id` from `app.current_tenant_id()` — inserts without `RETURNING` because the restrictive `scope_read` policy cannot see a row its own command made, reads the seven directory fields back in the same transaction, and appends the audit row before committing (T38, [`../adr/0008-people-write-path.md`](../adr/0008-people-write-path.md)). An update reads the current row first, writes only the columns whose effective value changed, and commits nothing at all when none did.
7. **Worker → PostgreSQL as `saas_worker`.** `runTenantJob` and the outbox pass/loop use the system-only `withTenantTransaction`, which checks platform access and an optional module entitlement gate but never a membership or role. The role holds no table privilege at all: it claims, publishes and fails events only through the four `SECURITY DEFINER` helpers granted in 0011, each of which filters on `app.tenant_id`. Delivery is at-least-once. There is no producer, no registered production handler and no deployed worker process; events reach the queue only through test fixtures inserted as `saas_owner`.
8. **CI.** GitHub Actions checks out the repository read-only, starts an ephemeral PostgreSQL service, installs with a frozen lockfile, scans tracked and untracked non-ignored regular files, audits production dependencies and runs the suites against localhost-only dummy credentials. There is now a GitHub remote — `Charanjitsingh1991/Saasmodelone`, connected private on 23 October 2026 and changed to **public** the same day at the owner's instruction (`gh api` reports `private: false`, `visibility: public`) — and the push of `f060bca` created Actions run `39903221917`, but no job has executed a step on GitHub: GitHub annotated the account as locked for billing, so attempt 1 never created the two matrix jobs and four reruns ended in `startup_failure` with zero jobs, and the post-public attempt 2 recorded `verify (postgres 16)` and `verify (postgres 17)` as started and completed in about two seconds with `runner_id: 0`, `runner_name: ""` and `steps: []`, each annotated `The job was not started because your account is locked due to a billing issue.` Making the repository public did not clear the lock, so no step of the list above has run.
9. **Web shell.** A React 19 + Vite SPA served on the application origin. In development and preview, Vite proxies `/v1` and `/health` to `127.0.0.1:3001`; production is expected to use one origin behind an edge or reverse proxy, which does not exist yet. The shell has `/login`, `/app` and `/app/people`, holds no session token in browser storage and renders module metadata from `/v1/context`. The People screen is a paginated, searchable directory with an inline add/edit panel that appears only when the context says the member can write People; it is not a CRUD surface — there is no delete, restore, status, placement, employment or user-linking control, no import and no export button — and no other module has a screen. Client routing is not an authorization boundary. One Playwright journey runs locally against the built output and a disposable database; it now creates and edits a person through the browser; it is declared in CI but CI has never run.

## 5. Disposition

### Mitigated and tested

T1, T2, T3, T4, T5, T6, T9, T11, T12, T14, T15, T16, T18, T19, T21, T24, T25, T26, T27, T28, T31, T32, T33, T34, T36, T37 and T38 have a control and a named automated test in the table above. Tests use a real disposable PostgreSQL database, the real runtime, auth and worker roles, real cookies and a real browser for the shell; they do not mock RLS, fetch, the session or the database. T36's testing has a stated limit that T19 narrowed: the `person` insert and update policies are now executed as `saas_runtime` through the write routes and through direct DML in `tests/scope.test.ts`, while `scope_delete` remains catalogue-only because the runtime role has no `DELETE` grant on `person` — deliberately, since no member-facing delete exists. T37's has two: the owner path is exercised through the library and the CLI against a real owner connection, so the CLI argument parsing and id resolution are proven by a manual run rather than by CI, and nothing in any test asserts that a *correct* grant was the *intended* one — approval, dry run and grant review do not exist.

### Mitigated but not tested

- T7 and T8 are partially mitigated: hashing, session expiry/revocation, uniform failures and in-memory rate limits are tested, but MFA, rotation, device binding, edge limiting and distributed limiting are absent.
- T10 relies on explicit parameterised SQL and code review; there is no dedicated injection test.
- T13 relies on streaming design and backpressure tests, but abuse resistance is not tested.
- T17 relies on the frozen lockfile, the local production audit and the workflow contract; the workflow has not run, and actions are not SHA-pinned.
- T20 has response tests, but production logging and redaction are not built.
- T23 relies on React escaping and the absence of any raw-HTML sink. The directory screen now renders stored person values, and the browser journey plus the seeded adversarial display names exercise that path in Chromium; since T19 a member with `people.write` can put arbitrary bounded text into those stored values through the panel, but the write suite validates shape and length rather than markup payloads, so there is still no CSP, no sanitisation library and no dedicated XSS suite over a wider payload set.
- T29 relies on exact pins, the frozen lockfile, the production-only audit and the workflow contract; there is no SBOM or provenance verification, and no CI job has executed a step on GitHub. The run created by the `f060bca` push, `39903221917`, ended its four attempt-1 reruns in `startup_failure` with zero jobs because the account is annotated as locked for billing, and its post-public attempt 2 recorded both matrix jobs with `steps: []` and the annotation `The job was not started because your account is locked due to a billing issue.` The repository is now public (`visibility: public`), so the source, migrations and this threat model are readable by anyone — a reviewer weighing T16 should note that the working-tree secret scan covers tracked and untracked non-ignored regular files and does not scan Git history or packed objects.
- T30 is mitigated only for the local preview proxy. No production edge or header set exists, so HSTS, CSP, frame-ancestors and proxy behaviour are unverified and must not be claimed.

### Not mitigated or accepted only for the M0 foundation

- T22 beyond the drill: retention, legal holds, offboarding, complete export and the audit read surface remain open; the `pnpm drill:restore` drill is partial mitigation for synthetic local data only.
- T35: outbox purge, dead-letter review, queue-depth alerting and pending-row caps do not exist. Nothing produces events in M0, so this is accepted only until the first producer lands.
- MFA, session rotation, device lists, distributed rate limiting and authentication-event audit.
- A dedicated export permission, export rate limiting and export history.
- The application surface for scope. 0012 enforces legal entity, org-unit subtree and employee self-scope in the database, `pnpm db:scope` (T37) writes `membership_scope` and `person.user_id` from the owner connection only, `GET /v1/people` narrows rows by those policies, and the write path now enforces `scope_insert` and `scope_update` on the same member transaction. Still absent: any API, UI or route that reads or writes scope, `/v1/context` reporting a member's scope, any scope label in the directory screen, and a runtime grant on either column or table. Project and client scope, role administration and seat enforcement do not exist.
- T38's accepted residuals, all of which are product gaps rather than bypasses: last-write-wins with no version column, so a concurrent edit overwrites without either member being told; no delete, restore or status route, so a junk create can only be renamed and no member can remove a row; uniqueness errors that confirm a code or email is taken without revealing it; no write rate limit; audit rows carrying field names only, so the trail cannot be used to undo an edit. None of these is closed, and the write path has no approval workflow in front of it.
- T37's accepted residual: a valid-but-wrong grant by an authorized operator. There is no four-eyes approval, no dry run, no alerting on a scope change, no scope-history report and no audit read surface, so detection is a manual owner-connection query.
- T36's accepted residual: a system transaction that sets `app.tenant_id` without `app.user_id` is not narrowed. That is what lets imports and background work span a tenant, and the only guard against a member route taking that path is import discipline and review. The two People read routes, the directory export and `GET /v1/people`, and the two write routes, `POST /v1/people` and `PATCH /v1/people/:id`, run in member transactions and are narrowed; the directory test is the first request-layer proof of that and the write test proves it for `scope_insert` and `scope_update`. Closing it needs either a route-layer assertion or a distinct role with no scope-escaping access.
- A named security owner, independent penetration test, incident exercise and production monitoring.
- Real customer data. It must not be loaded into M0.

## 6. Review questions

1. Are the two auth-table RLS exceptions (`auth_session`, `invitation`) acceptable, given the runtime role has no privilege on either and access goes through security-definer functions?
2. Is the person column-level grant narrow enough — eight `SELECT` columns for the export and directory read, and since T19 8 `INSERT` plus 6 `UPDATE` privileges for the write path, 22 column privileges with no table-level privilege — and should the three routes be its only callers by review rather than database enforcement?
3. What concurrency and size limits are required before an export route is exposed beyond synthetic data?
4. Which audit events and read surfaces are mandatory before a design partner imports real records?
5. Which open-source or hosted dependency and Action provenance controls are required before a Git remote is added?
6. What Content-Security-Policy, XSS regression suite and same-origin proxy verification are required before the People screen renders employee data?
7. Who owns the production edge, TLS and header configuration, and how will `Origin` preservation and SPA fallback be proven there?
8. Which producers may be wired first, what may an event `payload` contain, and what handler-review, payload-minimisation and queue-retention rules bind before a consumer runs against real data?
9. For T36: who owns the guarantee that a member request never reaches module data through `withTenantTransaction`, and is a route-layer assertion, a separate role or a required `app.user_id` predicate needed before the first scoped tenant is live? Which scope model lands next — project, client, or a manager-chain scope — and what evidence closes the fail-open residual?
10. For T37: who may hold `DB_OWNER_URL`, and is scope authoring acceptable as an owner-only CLI for a design partner, or does it need an authenticated admin surface with a second approver, a dry run and alerting first? What is the cadence for reviewing `membership.scope.changed` and `person.user.linked`, and who reads them while no audit read API exists?
11. For T38: is last-write-wins acceptable for identity fields, or does the directory need a version column, an `If-Match` style check or an edit lock before more than one member can write? Who may delete or correct a junk row when no member-facing delete exists, and does that make an owner-only archive step mandatory before real records land? Does a create need four-eyes approval, and is the `people.write` permission wide enough — HR can add a person to a tenant-wide directory with no legal entity attached? Should audit carry field names only, or is a redacted before/after value needed to make the trail useful for correction?

Until those questions have named owners and the design-partner gate is satisfied, this document is a draft, not an approval to handle real data.
