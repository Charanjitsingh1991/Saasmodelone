# Security and Privacy Baseline

Status: target baseline for the first design partner · October 2026
This is not a certification claim. It is the minimum bar before a real company's payroll data enters the product.

---

## 1. What we are protecting

| Asset | Why it matters | Classification |
| --- | --- | --- |
| Payroll, salary and bank details | Direct financial harm, insider risk | Restricted |
| Tax, social-insurance and national identifiers | Identity theft, statutory exposure | Restricted |
| Employment and performance records | Employee privacy, local privacy-law obligations | Confidential |
| Client contracts, invoices, margins | Commercial harm | Confidential |
| Documents and client room files | Confidentiality, contractual duties | Confidential |
| Credentials, API keys, signing keys | Full compromise if leaked | Secret |
| Audit trail | Trust, incident reconstruction | Restricted integrity |

Threats we design against first:

1. **Tenant escape** — a user reads or mutates another company's records.
2. **Entitlement bypass** — a user reaches a module the organisation has not licensed, or keeps access after cancellation.
3. **Privilege abuse** — an employee, HR user or insider sees salary or exports data they should not.
4. **Credential compromise** — reused passwords, stolen sessions, leaked API keys.
5. **Import poisoning** — a crafted CSV or connector payload corrupts payroll or injects content.
6. **Destructive mistakes** — an accidental edit to a finalised payroll run or a bulk delete.
7. **Export leakage** — signed URLs shared publicly, exports left in a bucket.
8. **Supply-chain compromise** — a malicious dependency or CI credential.

## 2. Tenancy

- Every tenant business table has `tenant_id` and RLS enabled (see `db/migrations/0001_core.sql`); missing `app.tenant_id` means no rows. The identity tables `auth_session` and `invitation` are the only exceptions: they carry `tenant_id` but deliberately have no RLS, the runtime role has no privilege on either, and they are reached only through security-definer auth functions.
- Runtime transactions set `app.tenant_id`; no setting means no rows.
- The runtime database role does not own tables and cannot bypass RLS.
- Cross-tenant foreign keys are prevented with composite `(tenant_id, id)` references.
- Tenant context is cleared when a pooled connection is returned.
- Automated table-level tests prove the restrictive module policies on the two M0 proof tables, `employment` (People) and `project` (Work): entitled access, denial for an unentitled module on an entitled tenant, denial for suspended, closed and deleted tenants holding an active entitlement, denial of cross-tenant reads and writes, and read-only access for a cancelled entitlement inside `read_until`. The matrix expands with each runtime table grant; it does not yet cover every tenant table.
- The API and worker share one tenant transaction. For request routes, the only source of tenant identity is the server-side session record resolved from the `saas_session` cookie; no header, query string, body or other cookie is trusted for it, and the raw token is never stored. Request routes use `withMemberTransaction`: both IDs are validated, `app.tenant_id` and `app.user_id` are set transaction-locally, and an active membership role is resolved before platform access, the module gate and the role permission. A non-member or suspended member receives `MEMBERSHIP_DENIED` before tenant state is disclosed; a member of a suspended, closed or deleted tenant receives `PLATFORM_ACCESS_DENIED`. The worker uses `withTenantTransaction`, which is system-only and does not check membership; it connects as `saas_worker`, a role with no table or column privilege that can only claim, publish and fail outbox events through the `SECURITY DEFINER` helpers in `0011_outbox.sql`, each of which filters explicitly on `app.tenant_id`. Email/password login, opaque hashed sessions and one-time invitation acceptance exist; MFA, OAuth, password reset, email delivery, session rotation, device lists, a distributed rate limiter and authentication-event audit do not. Role enforcement covers the two M0 gated modules (see §5). Scope enforcement is a database property from M1's `0012_people_scope.sql` (see §5.1), not a request-layer check: it applies to any transaction that set `app.user_id`, and by design narrows nothing on a system transaction that sets only `app.tenant_id` — that fail-open case is recorded as a residual in §5.1 and in threat row T36. `/v1/context` output is informational rather than an authorization decision. The context response is `Cache-Control: no-store`, returns only effective modules with their catalog names and sort order, and is not a substitute for a gate on any data route.
- Tenant provisioning is an owner-only library and CLI, never an API route. It creates the tenant, owner user, owner membership, entitlements and a `tenant.provisioned` audit event in one transaction, and prints only IDs. The runtime role has no `INSERT` on `tenant`. Invitation creation is also an owner-only CLI, not an API route. Login is scoped to a supplied tenant slug; there is no cross-tenant email discovery or tenant switching.
- The People directory export (`GET /v1/people/export`) is the first production module route. It is gated by `withMemberTransaction` with `{ module: 'people', operation: 'read' }`, so entitlement and role both apply, and tenant scope comes from `app.tenant_id` and RLS. The runtime role has column-level `SELECT` on seven identity fields plus `deleted_at` and the two placement ids, and no table-level `SELECT` on `person`; the export itself still reads only the seven, so the placement columns and the reference names never reach the CSV. Personal contact, demographic, status and statutory columns remain owner-only, and this CSV gains no employment column even after the employment-history routes landed — a history is a separate JSON read, never part of the export. The route commits a `people.directory.exported` audit row before the first CSV byte; an audit failure returns a sanitized 500 with no bytes. It reads through a server-side cursor in batches, honours backpressure, rolls back on client close, and prefixes formula-like leading characters before RFC 4180 quoting.
- The People directory write path (`POST /v1/people`, `PATCH /v1/people/:id`) is the first member write route. Both require a valid session and a matching `x-csrf-token`, checked with the same timing-safe comparison as logout and before any database work, so a cross-site form with a stolen cookie changes nothing; the `onRequest` origin hook still refuses another origin first with `ORIGIN_DENIED`. Inside, both run in `withMemberTransaction` with `{ module: 'people', operation: 'write' }`, so entitlement and role apply before the body is parsed, and the 0012 `scope_insert` / `scope_update` policies decide placement. Only the six identity fields are writable; an unknown key, a non-object body or an over-length value is `400 INVALID_BODY` with nothing echoed, `status`, `user_id`, `deleted_at`, the timestamps and the personal and demographic columns are unreachable by construction — and so are `legal_entity_id` and `org_unit_id`, which the identity route refuses as unknown keys and only the placement route below may write — and an out-of-scope, cross-tenant, soft-deleted, malformed or unknown target id answers one `404 PERSON_NOT_FOUND`. `saas_runtime` holds 10 `SELECT`, 8 `INSERT` and 8 `UPDATE` column privileges on `person` (26 in total), no table-level privilege and no `DELETE`. Writes append `person.created` / `person.updated` in the same transaction with field names only in metadata; an audit failure rolls the write back to a sanitized 500. See [ADR 0008](adr/0008-people-write-path.md).

- The People placement path (`GET /v1/people/placement-options`, `PATCH /v1/people/:id/placement`) is the first member-facing action that changes who can see a directory row, so it is gated as strictly as the writes and stricter than the reads. Both routes sit behind `{ module: 'people', operation: 'write' }`, including the options `GET`: a member who cannot place nobody has no reason to enumerate the tenant's legal entities and org units, and the read-only roles are refused `ROLE_DENIED` before a reference row is read. `PATCH` also requires session, exact `Origin` and the timing-safe `x-csrf-token`; the `GET` needs no token. The body is the closed two-key pair — exactly `legalEntityId` and `orgUnitId`, each a UUID or `null`, always the whole statement — so there is no omit-to-keep and a unit with a null entity is refused as `400 INVALID_BODY`. Every scope verdict is `app.person_placement_in_scope(legal_entity_id, org_unit_id)`, the same `SECURITY DEFINER` helper `scope_insert` and `scope_update` call; no scope rule is restated in the route, and the route never trusts the caller's claim that a pair is legal — it re-reads the unit and compares its own `legal_entity_id`. Out-of-scope, unknown, retired, cross-tenant or mismatched references answer `404 PLACEMENT_NOT_FOUND` and out-of-scope, unknown, soft-deleted or malformed people answer `404 PERSON_NOT_FOUND`, so neither route discloses the existence of a row the member cannot manage; only the both-null unplace, which has no id to hide, answers `403 SCOPE_DENIED`. `saas_runtime` gained column-only `SELECT` on `legal_entity (id, name, code, deleted_at)` and `org_unit (id, name, legal_entity_id, deleted_at)` — eight privileges, no table-level grant on either table, no write of any kind and no grant on their `tenant_id`; the runtime table-grant allowlist is unchanged at twelve rows. A change appends `person.placement.changed` in the same transaction with ids only (`legalEntityId`, `orgUnitId`, `previousLegalEntityId`, `previousOrgUnitId`) — no names, no emails, no field values — and a no-op placement writes neither the row nor the event. See [ADR 0009](adr/0009-people-placement.md).
- The People employment path (`GET /v1/people/:id/employments`, `POST /v1/people/:id/employments`, `PATCH /v1/people/:id/employments/:employmentId`) is the first product route to write `employment`, and the first place a read and a write against the same table are deliberately decided by two different scope predicates. The `GET` sits behind `{ module: 'people', operation: 'read' }` and applies no application-side scope check: the 0012 `scope_read` policy on `employment` calls `app.person_visible(person_id)` — the read oracle, the one that carries the linked-employee self exception — so a member who may see the person may open that person's whole history. Each write sits behind `operation: 'write'` and, in addition to the write-side policies, selects `app.person_in_scope(person_id)` inside the member transaction before any DML, so an unwritable person answers a typed `403 SCOPE_DENIED`. Both writes additionally require the session, an exact `Origin` and the timing-safe `x-csrf-token`, checked before any database work exactly as the identity and placement writes are; the history `GET` needs no token. That pre-check is not decoration: `saas_runtime` holds whole-table `INSERT`/`UPDATE` on `employment` from the M0 proof surface, so a denied write would otherwise fail with a `42501` privilege error or a zero-row update, and both were reaching the caller as a sanitized 500. `app.person_in_scope` is identical to `app.person_visible` except that `employee` is always false and a person linked to the caller gets no self exception — which is precisely why a history can be readable while every write on it is refused. [ADR 0010](adr/0010-people-employment.md) and threat rows T41 and T42 record the split, and `tests/people-employment.test.ts` pins it with a membership whose own linked person is visible-but-unwritable.
- What that path stores is closed and partly derived. A create accepts `employmentType`, `startDate` and the optional `endDate`, `probationEndDate` and `noticeDays`; a patch may additionally name `status`, and an absent key means unchanged while an explicit `null` clears only those three optionals. There is no `personId` (the path supplies it), no `legalEntityId` — the entity is copied from the person's placement at the moment of the write, so an unplaced person or one placed on a soft-deleted entity is a `409 EMPLOYMENT_ENTITY_REQUIRED` and the row keeps the entity it was written against even after the person moves — and no `status` on a create, because `status` is absent from the insert column list and the column default is its only source. `work_jurisdiction_id`, `source_system`, `source_id`, `import_batch_id`, `tenant_id` and the timestamps are named by no route, and a body key outside the closed list is `400 INVALID_BODY` with nothing echoed. Dates are `YYYY-MM-DD` strings checked for shape *and* for being a real day (`2026-02-30` and `2025-02-29` are refused, `2024-02-29` is not), never `Date` objects, so no timezone can shift a stored day; `notice_days` is bounded at `EMPLOYMENT_NOTICE_DAYS_MAX` rather than left at the table's `>= 0`. Lifecycle is validated in the same transaction: an end or probation date cannot precede the start, `ended` requires an end date, and a status moves forward only — `active → ended` and `active → cancelled` are legal, an `ended` or `cancelled` row never returns. Existence is not disclosed: a person id that is unknown, cross-tenant, soft-deleted, malformed, or an entity id or the person's own employment id used in its place answers one `404 PERSON_NOT_FOUND`, and an employment id that is not a row of that person answers one `404 EMPLOYMENT_NOT_FOUND`. A successful write appends `employment.created` / `employment.updated` with the employment's own id as entity ID and field names only in metadata — no date, no notice period, no status — in the same member transaction, so a revoked audit grant rolls the write back to a sanitized 500 with the row unmoved. Nothing here is a new privilege, policy, helper or migration.
- The People compensation history read (`GET /v1/people/:id/compensations`) is the first route anywhere in the suite behind a permission that the module's own read does not imply. It runs in `withMemberTransaction` with `{ module: 'people', operation: 'read', permission: 'people.compensation.read' }`, so the fixed order still holds and an unentitled tenant answers `MODULE_NOT_ENTITLED` for this path exactly as for every other — it never learns the permission exists — while a role without the new name answers `ROLE_DENIED` naming it, before the person id is looked at. The route is a `GET`: no CSRF token, no state change, and `Cache-Control: no-store` on every response, refusals included. Rows are narrowed underneath by `compensation.scope_read`, the ninth restrictive scope policy (`as restrictive for select using (app.person_visible(person_id))`, added by `0013_compensation_read.sql`), which is the same read oracle the directory and the employment history use; the route states no scope rule of its own, and the person read that gates the list is the directory's own select, so an unknown, cross-tenant, soft-deleted, malformed or out-of-scope person id answers one `404 PERSON_NOT_FOUND` and the route cannot be used to probe for people a member may not list. `saas_runtime` holds seven column `SELECT` privileges on `compensation` (`id`, `person_id`, `effective_from`, `effective_to`, `ctc_minor`, `currency`, `pay_frequency`), no table-level privilege and no `INSERT`, `UPDATE` or `DELETE` of any kind: `structure`, `source_system`, `source_id`, `import_batch_id`, `imported_at`, both timestamps and `tenant_id` are unreadable through the runtime role, and at that slice no route in this build wrote a salary figure — the two routes below are the change. Money is disclosed as stored and never converted — `ctc_minor` is selected `::text`, parsed with `Number.parseInt` and refused with a sanitized `500 INTERNAL_ERROR` once it leaves `Number.isSafeInteger`, so a bigint JavaScript cannot hold never arrives as a rounded number; amount, currency and pay frequency are three independent values in the response and no layer annualises, prorates or period-labels them. A refusal appends exactly one `authorization.denied` row whose metadata is the six reviewed keys — reason, module, operation, permission, method and the `/v1/people/:id/compensations` template — with no person id, no amount and no currency in it; a successful read appends nothing, which is a pinned absence rather than an oversight and is recorded as a residual on threat row T43. The directory export gains no column: `tests/people-compensation.test.ts` streams the CSV byte-identical with salary rows present. See [ADR 0011](adr/0011-compensation-read.md).

- The People compensation write path (`POST /v1/people/:id/compensations`, `PATCH /v1/people/:id/compensations/:compensationId`) is the second route family anywhere in the suite behind a permission its module does not imply, and the first place a read oracle and a write oracle disagree on the same table. Both run in `withMemberTransaction` with `{ module: 'people', operation: 'write', permission: 'people.compensation.write' }`, so an unentitled tenant is refused the module before the permission is discussed and a role without the name is refused `ROLE_DENIED` naming it — `manager`, `auditor` and `employee`, including the employee whose own linked person the read oracle would have shown. Both additionally require the session, an exact `Origin` and the timing-safe `x-csrf-token`, checked before any database work. Inside the transaction the order is fixed and none of it is a scope decision: the two UUID guards, then the person read through the directory select as the visibility test (unknown, cross-tenant, soft-deleted or malformed is one `404 PERSON_NOT_FOUND`, so a caller cannot probe the pay path for people it may not list), then `select app.person_in_scope($1)` — the **write** oracle, with no self exception and always false for `employee` — answered `403 SCOPE_DENIED` before the body is parsed, then validation, then the DML. No scope predicate is restated in a `WHERE` clause. `0014_compensation_write.sql` adds exactly the two restrictive policies (`scope_insert` with `check (app.person_in_scope(person_id))`, `scope_update` with the same predicate in both halves), and the grant adds exactly two column-qualified commands: `INSERT` over `id`, `tenant_id`, `person_id`, `effective_from`, `effective_to`, `ctc_minor`, `currency`, `pay_frequency` and `UPDATE` over the five business columns only. `compensation` therefore sits at twenty column privileges over eight columns with still no table-level privilege for any of seven commands and still no `DELETE`: the `WITH CHECK` half is what would refuse a re-parented row and the missing `person_id` update privilege is what refuses it first, and a runtime `delete from compensation` is refused `42501` because there is nothing for a delete policy to govern. Neither statement uses `RETURNING` — a server-generated id from `node:crypto`'s `randomUUID()` and an explicit column list, then a read-back through the same `COMPENSATION_SELECT` the panel already uses, so the write answer and the read answer are one shape — and on this table `RETURNING` would in fact have been permitted, because `compensation.scope_read` evaluates an existing `person_id` rather than the new row's own id, which is why `person` refuses it and `compensation` does not; the difference is pinned by a probe test rather than assumed. Validation refuses rather than coerces: closed key sets, `YYYY-MM-DD` checked as a real day, `ctcMinor` an integer in `0 … Number.MAX_SAFE_INTEGER` with no rounding path and no float, `currency` exactly three ASCII `A`–`Z` never upper-cased so `inr` fails and `ZZZ` stores, one of four published frequencies, `effectiveTo` at or after the merged `effectiveFrom`, and a patch that names no known field is `400 INVALID_BODY`. The only period rule is the table's own `unique (tenant_id, person_id, effective_from)`, whose `23505` answers `409 COMPENSATION_PERIOD_EXISTS`; overlapping periods are accepted because inventing a non-overlap rule would be inventing a business rule, and that is threat-model review question 15. A patch whose merged values all match the stored row writes neither the row nor an audit event, and a `rowCount` other than one rolls both back as a sanitized 500. Writes append `compensation.created` / `compensation.updated` with `entity_type = 'compensation'`, the row's own id as entity ID and metadata `{ fields: [...] }` — the names that moved, never an amount, never a before/after — in the same member transaction, so a revoked audit grant rolls the write back; a `SCOPE_DENIED` leaves no audit row, on the same rule ADR 0008 §13 and ADR 0009 §14 keep. The directory export gains no column and no byte: `tests/people-compensation-write.test.ts` asserts the CSV identical before and after a salary write. See [ADR 0012](adr/0012-compensation-write.md) and threat row T44.

- `FORCE ROW LEVEL SECURITY` is not enabled in a migration. A readiness test temporarily forces it on `tenant`, proves that provisioning still sets `app.tenant_id` before the tenant insert, and resets it. Global reference tables and `infra.schema_migration` are never forced.

## 3. Module entitlements

- The module catalog (`platform_module`, `platform_module_dependency`) is reference data. The runtime role can read it and cannot write it.
- Each tenant has `module_entitlement` rows for licensed modules, with status, seat unit, start/end dates and contract reference. RLS scopes entitlements to the tenant. `read_until` is set if and only if the entitlement is cancelled; it is null for every other state.
- Authorization order is **entitlement → role → scope**. A user with the right role in the wrong module is still denied. M0 implements the entitlement and role checks in the request path. Scope is enforced underneath them in the database from `0012_people_scope.sql` (see §5.1): the request layer still makes no scope decision, and the order is preserved because a scoped member's rows only appear once entitlement and role have passed.
- Module access has one database definition, split by operation: `app.has_module_read('<code>')` and `app.has_module_write('<code>')`, both security-definer. Every module helper first requires `app.has_platform_access()`: a tenant context is set and the tenant is active and not deleted. Write requires a trialing/active entitlement inside its window; read additionally allows suspended entitlements inside their original term and cancelled entitlements inside `read_until`. Post-term retention is `cancelled` plus `read_until`, never a stale suspension. Public tenants can use only `available`/`preview` catalog modules; `planned` modules require `tenant.is_internal` and an internal-source entitlement. `app.has_active_module('<code>')` is the exact delegate to the write helper, kept for compatibility; new SQL uses the read/write helpers, and no helper is ever called with `'core'` or `'switch'`.
- Module tables carry `as restrictive` RLS policies installed by the idempotent, owner-only procedure `app.apply_module_policies()`; the runtime role has no `EXECUTE` on it. Switch staging is gated by `app.has_switch_access()` — any trialing/active licensable entitlement inside its window and an active tenant — never by a Switch entitlement.
- `tenant.is_internal` is set only by the provisioning path; the runtime role has no `UPDATE` on `tenant`.
- Tenant-level suspension, closure and soft deletion are denied at both layers: `app.has_platform_access()` at the request layer, and every module RLS policy through the module helpers.
- Cancellation and expiry remove access but never delete module data. Read/export access for a cancelled module is an explicit retention decision, not a side effect of the entitlement being absent. The People directory export follows `has_module_read`, so a cancelled People entitlement inside `read_until` can still export; outside that window the route returns `MODULE_NOT_ENTITLED`.
- Entitlement changes go through the owner-only `grantEntitlement` / `cancelEntitlement` library, never the API. Grant upserts an `active` (the default) or `trialing` entitlement, clears a previous `read_until`, preserves `created_by` and validates the same catalog rules as provisioning. A `trialing` entitlement requires an explicit `endsAt` after `startsAt`; open-ended trials are rejected. A public tenant may use `contract` or `trial` sources only; source `internal` requires `tenant.is_internal`. Cancel requires an existing entitlement, sets `cancelled` plus a future `read_until`, keeps the original start/end dates, never deletes data and allows extending an existing retention window.
- Entitlement changes are audited with actor, module, previous state and new state. Contract references are deliberately excluded from audit snapshots; cancellation reasons live in audit metadata only. The runtime role can read entitlements but cannot change them.
- Membership roles resolve through `app.current_member_role()`, a security-definer helper pinned to the current tenant and user. The runtime role has no `SELECT` on `membership`, `membership_scope`, `app_user` or `tenant`. The stored role is validated against the seven allowed values in the request layer; an unknown value is a data-integrity error and is never treated as a permissive default.
- A dependency that is optional does not imply a licence: Work can run without CRM or People, and the UI must hide or degrade the dependent feature rather than leak data from an unlicensed module.
- API tokens carry module scopes; a token cannot be used to call an unentitled module even if the role allows it.

## 4. Identity and sessions

Implemented in M0:

- Email/password with Argon2id (19,456 KiB, time cost 2, parallelism 1, 32-byte output). Passwords are 12–128 characters, never trimmed, with no composition rules. A missing email, wrong password, non-member, suspended membership or ineligible user all perform an Argon2 verification and return the same `INVALID_CREDENTIALS` response.
- Identity is global: `app_user.email` is unique across the platform, one row per person. Memberships are per tenant, so one user can hold a membership in several tenants. Login requires a tenant slug and selects that user's membership in that tenant; the same password is used across all of that user's memberships. There is no cross-tenant email discovery or tenant switching.
- Opaque sessions: 32 random bytes carried in an `HttpOnly`, `SameSite=Strict`, `Path=/` cookie, `Secure` when configured, with a 12-hour absolute expiry. Only the SHA-256 hash is stored. Logout requires the session's CSRF token and revokes only the presented session.
- One-time invitations created by the owner-only `db:invite` CLI, hashed at rest, 7-day default expiry (1–30 days). Creation revokes older unconsumed invitations for the same membership. Acceptance activates the invited membership and creates a session in one transaction. A first-time invitee sets a password; an already-active user invited to a second tenant keeps and verifies its existing password, which is never replaced. Acceptance is rejected if the user is active but has no password, or if the password does not match.
- State-changing requests require an exact `Origin` match. Login is rate-limited in memory per process by source address and additionally per email; invitation acceptance is rate-limited per source address. The limiter uses the observed socket address, so behind a proxy without `trustProxy` all clients share the proxy address; it is not a distributed limiter and not a replacement for edge protection.
- Every login creates one session. A session proves identity only and grants no action by itself: each member request resolves the membership role server-side, and a module gate requires both the entitlement and the role permission. Scope is then applied by the database policies that the same transaction's `app.user_id` feeds (see §5.1), not by the request layer.
- The web shell never receives the session token. The `saas_session` cookie is HttpOnly; the CSRF token needed for sign-out is kept only in module memory, and credentials are never written to local storage, session storage, the URL or logs. The theme is the only persisted preference. Client routing and module hiding are not authorization: the server repeats the entitlement and role checks on every request and the database applies the scope policies underneath them. A sign-in rejection shows one generic message; a `429` has a distinct message; any `401` after sign-in clears in-memory state and returns to sign-in. Of these behaviours the browser journeys in `testing.md` §2.13 cover only the generic sign-in rejection message; the distinct `429` message is covered only by the login-mapping unit tests in `apps/web/test/errors.test.ts`; the post-sign-in `401` clear has no test and rests on code inspection. None is covered by a production CSP or proxy-header test.

Target controls, not built:

- MFA for owners, admins, HR and finance; OAuth (Google and Microsoft), SSO (SAML/OIDC) and SCIM.
- Password reset and email delivery, session rotation, device lists and session management UI.
- Scoped, hashed, one-time-displayed API keys.
- Edge brute-force and credential-stuffing protection beyond the per-process limiter.
- Time-boxed, audited support impersonation. No shared accounts.

## 5. Authorization

Implemented in M0:

- Server-side role authorization after the module entitlement check. `withMemberTransaction` resolves the active membership role, checks platform access, checks the module entitlement, then checks the role permission before the route callback. The order is fixed: an unentitled module never discloses which roles could use it.
- The policy is shared code in `@saasmodels/contracts`: `MEMBERSHIP_ROLES`, `PERMISSIONS`, `permissionsForRole`, `hasPermission` and `permissionFor`. It covers the two M0 gated modules, People and Work, and fails closed for an unknown role, an unknown permission or an unmapped module/operation pair. Since T22 a gate may also name the permission it needs instead of deriving it from module and operation — `{ module: 'people', operation: 'read', permission: 'people.compensation.read' }`, and since T23 `{ module: 'people', operation: 'write', permission: 'people.compensation.write' }` — which keeps the module and operation vocabulary intact (`MODULE_OPERATIONS` is still `read`/`write`) while letting one route ask a narrower question than its module's read or write. `assertGate` rejects a name outside `PERMISSIONS` or outside the gate's own module, so an override cannot turn a `people` route into a `work` check, and the entitlement test still runs before the permission test.
- Matrix (✓ = allowed; the seven columns are `people.read`, `people.write`, `people.compensation.read`, `people.compensation.write`, `work.read`, `money.read` and `content.read`, in `PERMISSIONS` order):

| Role | People read | People write | Pay read | Pay write | Work read | Money read | Content read |
| --- | --- | --- | --- | --- | --- | --- | --- |
| owner | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| admin | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| hr | ✓ | ✓ | ✓ | ✓ | | | |
| finance | ✓ | | ✓ | ✓ | ✓ | ✓ | |
| manager | ✓ | | | | ✓ | | |
| employee | | | | | | | |
| auditor | ✓ | | | | ✓ | | |

- `work.write` was withdrawn on 27 October 2026, so the published set is seven names and the six-column matrix is gone. It was the only published permission no route asked for, and while it stayed published `/v1/context` answered `canWrite: true` for Work — a capability the product cannot perform and no screen offers. `permissionFor` derives from `PERMISSIONS`, so `permissionFor('work', 'write')` now answers `null` and the context answers `canWrite: false` for Work with no change to the route that asks. Two cells moved in the same edit: `manager` lost the Work write it never had a route behind, and `finance` gained `money.read`, because invoices are what a finance role reconciles. `auditor` gained neither `money.read` nor `content.read`: an audit role is built for aggregates and reconciliation, and this product builds neither, so the exclusion is recorded as a residual on threat row T45 and asked as review question 16. The `hr` row is a first cut too — it reads no Content, and whether it should is the second half of that question.
- The three module read permissions are published as reads because a module that can only be read is published as a read: a write that is not built is not published at all. There is no `work.write`, no `money.write` and no `content.write` to gate, and no product write route in any of the three modules — each ships exactly one `GET` route and nothing that creates, changes or removes a row — so `tests/authorization.test.ts` pins that `permissionFor` answers `null` for each of those pairs and that no role holds one.

- The two compensation permissions are the two that no other permission implies. `people.compensation.read` is third in `PERMISSIONS` and `people.compensation.write` fourth, both beside the same four roles — the four that maintain or pay people — and both refused to `manager`, `auditor` and `employee`. Holding `people.read` lists every colleague in scope and says nothing about whether you may see or change what one of them costs; holding `people.write` renames a colleague and says the same. `manager` is refused as the case a customer is likeliest to contest, and `auditor` is refused as a policy choice — an audit role is built for aggregates and reconciliation, and this product builds neither — which is recorded as a residual on threat rows T43 and T44 and asked as review questions 14 and 15.
- The axis the pair opens is visible in the `finance` row: that role holds the pay read and the pay write and is refused `people.write`, because maintaining a salary row touches the `compensation` table only and needs no say over a colleague's name or placement. No single `people.write` permission could have expressed that, and `hr` — which maintains the person and the pay — holds both writes. `admin` holds every published permission as the owner's delegate everywhere except the owner-only scope authoring. `tests/authorization.test.ts` pins the matrix and, with it, that no role holds one compensation permission without the other and that `permissionFor` never answers with either, so a gate that names no permission can never widen into a salary read or a salary write by accident.
- `employee` is intentionally empty. 0012 added the person-to-user link and the self-scope policy in the database, and T22 and T23 added two permissions without giving either to this role, so an employee request still returns `ROLE_DENIED` before any scope policy is reached — including the compensation read, where the policy would have shown the member their own row. The write is the sharper case: `app.person_in_scope` has no self exception and is false for `employee` whatever else is true, so licensing this role would need the permission *and* a decision about self-maintenance, which is why `tests/scope.test.ts` proves an employee can never write through SQL scope even for its own row. Giving the role a permission is later M1 work and needs its own review.
- The employment path is where that empty row hurts most visibly: `tests/scope.test.ts` proves an employee's own linked history *is* readable at the policy level — "gives an employee exactly the linked person row and nothing else" — and that the same employee can never write through it — "lets an employee read but never write through SQL scope, even for their own row" — but `GET /v1/people/:id/employments` denies that member `ROLE_DENIED` on `people.read` before either policy runs. There is therefore no employee-facing employment history in the product, and the working database half of it is not evidence of a feature.
- The matrix was unchanged by T19, T20 and T21, moved for the first time in T22 when it gained the pay read column, and gained a second pay column in T23 for `people.compensation.write`: in both slices the four roles that already read or maintain people gained the new permission and `manager`, `auditor` and `employee` did not, so neither move altered an existing cell. It moved twice more on 27 October 2026: the Work write column was withdrawn outright, and the Money read column was added for `finance` alone. **Every ✓ cell now has routes behind it.** `people.write` is checked by `POST /v1/people`, `PATCH /v1/people/:id`, `PATCH /v1/people/:id/placement`, `POST /v1/people/:id/employments`, `PATCH /v1/people/:id/employments/:employmentId` and — deliberately, for a read — `GET /v1/people/placement-options` (§2), the routes that demand it, and by none of the two compensation writes. `people.read` is now asked by the directory page, the export and `GET /v1/people/:id/employments`; `people.compensation.read` is asked by `GET /v1/people/:id/compensations` and by nothing else, and `people.compensation.write` by `POST /v1/people/:id/compensations` and `PATCH /v1/people/:id/compensations/:compensationId` and nothing else, which is what makes each a real narrowing rather than a second name for the same door. `work.read` is asked by `GET /v1/work/projects`, `money.read` by `GET /v1/money/invoices` and `content.read` by `GET /v1/content/items`, each by nothing else, so each of the three is a permission with exactly one route behind it.
- There is no employment-specific permission. A history is read with `people.read` and written with `people.write`, so anyone who can edit a person's name can add or amend that person's employment dates, and anyone who can see the directory can see the employment dates of everyone in it; a `people.employment.read` or `people.employment.write` pair is M1 work and is recorded as a residual on threat row T41.
- A role that holds the permission for an entitled module proceeds; an entitled module with a role that lacks the permission returns `ROLE_DENIED` with the permission name and no data; an unentitled module returns `MODULE_NOT_ENTITLED` regardless of role.
- `/v1/context` reports the role's permissions in canonical order, including permissions for modules the tenant has not licensed, plus only the effective modules where the database entitlement and the role permission both allow the operation. Context output is informational; the server repeats the check on every request.
- Authenticated access denials are audited as `authorization.denied` (see §7). The audit is best-effort and cannot turn a denial into an allow.

Target controls, not built:

- Scope values in the UI or in `/v1/context`, and project and client scope. The database half — legal entity, org-unit subtree and employee self-scope — landed in `0012_people_scope.sql`, the first request-layer consumer landed with `GET /v1/people`, and the placement path is the first place a member action changes the value scope keys on (see §5.1): the directory route and screen show only what the policies allow, and the placement panel offers only the entities and units the same helper approves — but they enforce scope without displaying it, and no client can tell a tenant-wide member from a scoped one. There is still no API or UI that reads or writes a membership's own `membership_scope` rows or the person/user link; the only path for those is the owner-only `db:scope` CLI in §5.1, and legal entity and org unit administration has no route at all.
- Role administration API or UI, custom roles, seat enforcement and per-entity licensing.
- Sensitive permissions beyond the seven published ones — the four M0 module permissions, the compensation read and write T22 and T23 added, and the three module reads Work, Money and Content added on 27 October 2026 — are target state: payroll finalise, bank change, role change, a dedicated export permission, delete and connector credentials. `people.compensation.write` was on that list until T23; it is now a name, a gate, two routes and two column-qualified grants, and what remains unbuilt around it is the control a money write would want — an approval, an undo, a delete, a read surface for the audit trail, and any rule for what `ctc_minor` is a figure *of*. The M0 People directory export is gated by `people.read`; it does not add or imply a dedicated export permission, which is M1.
- **The three module read permissions have no write half at all.** `work.write`, `money.write` and `content.write` are not published, so there is no permission to gate, no grant to issue for one and no product write route in any of the three modules. `permissionFor` answers `null` for each of the three pairs and `/v1/context` answers `canWrite: false` for Work, Money and Content, which is what the client reads when it decides not to render a write control. A module that cannot write is published as a read, and nothing else.
- Four-eyes approval for payroll finalisation and bank-detail changes above a configurable threshold.
- Client contacts as a separate principal type with document-room-only access.
- A module administrator who can administer one module without becoming a tenant owner.
- A production Content-Security-Policy, HSTS and the rest of the edge header set, verified against a real deployment. The web shell has no CSP today, renders no user-supplied content and uses no third-party runtime script, so this gap is documented rather than claimed as mitigated.

### 5.1 Scope authorization (M1)

`suite/db/migrations/0012_people_scope.sql` adds the first scope layer. It narrows
access only: every policy it installs is `AS RESTRICTIVE`, so it can remove rows an
M0 member could already see and cannot add one. Design and reasons are in
[`adr/0007-people-scope.md`](adr/0007-people-scope.md).

- `membership_scope` records one legal entity or one org unit per row, with a CHECK that forces exactly the matching typed column and a `NULLS NOT DISTINCT` unique so a scope cannot be granted twice. `person.user_id` links a directory record to the user who signs in as it, unique per tenant and `ON DELETE SET NULL`.
- The authoring path for both is owner-only and out of band: `packages/db/src/scope.ts` (`linkPersonUser`, `unlinkPersonUser`, `setMembershipScope`, `getMembershipScope`) behind the `pnpm db:scope` CLI, which connects with `DB_OWNER_URL` and is never reachable from the API. Every tenant, actor, membership, person and scope-target check is a tenant-scoped query written by hand, because the owner role bypasses RLS by ownership rather than by trusting the caller. Each accepted change appends its audit row in the same transaction, so an audit failure rolls the change back; a no-op writes no row. `tests/scope-admin.test.ts` covers it, including the real `23503` audit-failure rollback.
- Fixed resolution order inside the helpers: no `app.user_id` → no narrowing; no tenant or no active membership → denied; `employee` → own linked person for read and never for write; a role outside the six manageable roles → denied; zero scope rows → tenant-wide; otherwise the placement must match the member's legal entity, or their org unit or any descendant of it. An unplaced person is visible only to a tenant-wide member. `setMembershipScope` refuses an `employee` membership outright: scope rows there would be dead data that cannot widen self-scope.
- The decision is a database property: restrictive `scope_*` policies on `person` and `employment` call `app.person_visible()`, `app.person_in_scope()` and `app.person_placement_in_scope()`. These are owner-owned `SECURITY DEFINER` functions with `set search_path = ''`, revoked from `PUBLIC`, `EXECUTE` granted only to `saas_runtime` through `packages/db/sql/runtime-grants.sql`. `saas_runtime` and `saas_worker` have no privilege on `membership_scope`, so a member's scope is never readable as a table and the administration library stays on the owner connection.
- A scope row can never widen an employee: self-scope is a ceiling. The `employee` permission set is unchanged, so today an employee request denies at `ROLE_DENIED` before a scope policy is reached.
- **The first request-layer consumer enforces scope without displaying it.** `GET /v1/people` — the directory read route behind the People screen — runs its page query and its `count(*)` inside one `withMemberTransaction` with the People read gate, so `app.user_id` is set and the restrictive policies decide both which rows and which total come back. The route contains no scope predicate in SQL or TypeScript, and `tests/people.test.ts` pins the regression: a manager scoped to one legal entity reads exactly one row through the route while the tenant owner reads the whole tenant in the same run. The directory export, registered earlier, sits behind the same helper and is narrowed the same way. What the layer does **not** expose: `/v1/context` still carries entitlements and permissions only, no screen prints a scope label, and no API returns a member's scope rows — a client cannot distinguish a tenant-wide member from a scoped one, so the honest UI copy says only that the view is limited by role and scope.
- **The write path is the second consumer, and the first to exercise the write-side policies.** `POST /v1/people` and `PATCH /v1/people/:id` (§2) run inside the same member transaction, so `scope_insert` and `scope_update` decide placement and row reach rather than any application check: a member whose scope is one legal entity cannot create an unplaced person — the route asks `app.person_placement_in_scope(null, null)` before inserting and answers `403 SCOPE_DENIED` — and cannot edit a person outside their scope, which answers the same `404 PERSON_NOT_FOUND` as a cross-tenant or soft-deleted target. `tests/scope.test.ts` now drives real DML through those policies instead of only asserting they exist, and `tests/people-write.test.ts` pins the route-level narrowing: an in-scope edit succeeds, an out-of-scope id on the same row 404s, and a scoped manager's create is refused while a tenant-wide manager's create is accepted. Nothing about the write path widens a scope, and no scope value is displayed.
- **The placement path is the third consumer, and the first that changes what scope sees.** `GET /v1/people/placement-options` and `PATCH /v1/people/:id/placement` (§2) do not merely run under the policies: they ask `app.person_placement_in_scope` for every verdict — `canUnplace` for the both-null call, each entity's `placeable` flag for the entity-only call, each unit for its own pair, and the pair being stored for the write — so the offer list a member sees is produced by the same definer `scope_insert` and `scope_update` use, not by a second implementation of the rule in the request layer. A member scoped to one legal entity can move people within it, can place on nothing else, and cannot remove a placement at all (`403 SCOPE_DENIED`, the only case with no id to keep opaque); a member scoped to an org unit gets that subtree grouped under a parent marked not placeable. The effect is bidirectional: placing a person decides whether `member_placement_matches` approves it, so an in-scope move can bring a colleague into a member's directory and an out-of-scope or unplacing move takes them out. `tests/people-placement.test.ts` pins both directions through the route, and `tests/scope.test.ts` continues to drive the policies with real DML. No scope row is read, written or displayed by these routes; `membership_scope` and `person.user_id` keep zero runtime privileges, and `db:scope` stays the only authoring path for them.
- **The employment path is the fourth consumer, and the first to treat the read oracle and the write oracle as different things.** `GET /v1/people/:id/employments` (§2) runs no application-side scope check at all and is narrowed only by `employment`'s restrictive `scope_read`, which calls `app.person_visible(person_id)` — the read oracle, with the linked-employee self exception. `POST /v1/people/:id/employments` and `PATCH /v1/people/:id/employments/:employmentId` run under `scope_insert` / `scope_update`, which call `app.person_in_scope(person_id)`, and additionally select that same helper before touching a row. The two helpers differ in exactly one respect — an employee is always false for write, and a person linked to the caller gets no exception there — so the pre-check is not redundant: without it a denied employment write surfaces as the `42501` privilege error or a zero-row `UPDATE`, because `saas_runtime` holds whole-table `INSERT`/`UPDATE` on `employment` from the M0 proof surface and the policy refusal is the only gate. `tests/people-employment.test.ts` drives a membership whose own linked person is policy-readable and helper-unwritable, and asserts that both writes answer `403 SCOPE_DENIED` with the table left byte-identically unchanged while the same membership still reads the history; `tests/scope.test.ts` continues to prove the policy split underneath. The consequence for one screen is that scope is now decided three ways on the same directory row — who can see the person, who may change that person's identity or placement, and who may add or amend their employment — and only the first is the read oracle. Nothing in this path reads, writes or displays a scope row, and no policy, helper, grant or migration changed to build it.
- **The compensation read is the fifth consumer, and the first on a third table.** `GET /v1/people/:id/compensations` (§2) is narrowed by `compensation`'s restrictive `scope_read` — 0013's one policy, calling the same `app.person_visible(person_id)` read oracle the directory and the employment history use — and the route adds no scope statement, no helper call and no ordering by amount. It is also the first table whose read policy landed in the same slice as its read grant, because `tests/scope.test.ts` discovers every public `person_id` table the runtime can reach, by table-level or any column-level `SELECT`, and refuses one with no restrictive read policy. Before 0013 the table was invisible to the runtime, so the seven column grants on their own would have opened an unscoped read of every salary row in the tenant; the policy is what makes the grant a narrowing instead of a hole. The permission in front of it is a separate question from scope, not another spelling of it: entitlement, role and then these policies decide whether the module is licensed, what kind of action a member may take and which rows the answer contains, so a tenant-wide `hr` member reads every colleague's pay history and an entity-scoped one reads only the people that entity can already list.
- **Residual, deliberate and pinned.** A transaction that sets `app.tenant_id` but not `app.user_id` — every `withTenantTransaction` path, including the worker gate and the module-RLS suites — sees the whole tenant. System paths need that, and an unset GUC cannot be distinguished from an empty one, so the guarantee is that member routes use `withMemberTransaction`, which is import discipline and code review, not a database guard. `tests/scope.test.ts` pins the behaviour so any change is a failing test; threat row T36 records it. The residual is about routes that do not exist yet: every current member data route takes the member helper, and a future one that shortcuts to the system helper would silently return the whole tenant.
- Threat row T37 records the other side: the owner-only authoring path itself. An operator with `DB_OWNER_URL` can link a person to the wrong user or grant an over-broad scope, and both land as tamper-evident audit rows, but there is no audit read API or UI, so detecting a bad grant is a manual query on the owner connection.
- Not built: scope for project and client, any API or UI that reads or writes scope, scope values in `/v1/context` or in any screen label, and role or seat administration.
- **The compensation write is the sixth consumer, and the second table where the two oracles differ.** `POST /v1/people/:id/compensations` and `PATCH /v1/people/:id/compensations/:compensationId` (§2) are narrowed by 0014's two restrictive policies, both calling `app.person_in_scope(person_id)` — the write oracle — beside the read policy that still calls `app.person_visible(person_id)` on the very same table. `compensation` is now the third table carrying an insert and an update policy, after `person` and `employment`, and the pair arrives with the two column-qualified grants rather than a table-level one, so `has_table_privilege` is still false for every command and there is still no `DELETE` to narrow. The route asks the write oracle before the DML for the reason T42 found on `employment`: a read that succeeded says only that a caller may see the person, and `person_in_scope` deliberately has no self exception, so a member's own linked row stays readable and unwritable here too. One asymmetry is worth stating plainly: the grant-to-policy coupling `tests/scope.test.ts` enforces discovers *readable* tables, so nothing in the harness would have caught a write grant shipped without a write policy — the 0014 pair was matched to the grants by review and by the suite's pinned clause list, which ADR 0012 records as a harness gap rather than as covered. `tests/scope.test.ts` asserts the invariant that every runtime-readable table with a `person_id` column carries a restrictive read policy calling `app.person_visible(person_id)`; discovery is by grant, not by an exceptions list, so that set is `employment` and — since 0013 landed its grant and its policy in one slice — `compensation`.

### 5.2 Module read surfaces (M1)

Work, Money and Content became readable on 27 October 2026, by the owner's decision to build all five modules rather than one at a time; CRM has no tables in the schema, so this batch is these three. The design is in [ADR 0013](../adr/0013-work-money-content-read.md) and threat row T45 carries the residual.

- `GET /v1/work/projects`, `GET /v1/money/invoices` and `GET /v1/content/items` are gated `{ module: 'work', operation: 'read' }`, `{ module: 'money', operation: 'read' }` and `{ module: 'content', operation: 'read' }`. Entitlement is answered before role, so an unentitled tenant learns nothing about which roles could use the module, and a role that lacks the permission is refused with `ROLE_DENIED` and no data. All three run inside `withMemberTransaction`, so `app.tenant_id` is set and the restrictive policies `module_work_read`, `module_money_read` and `module_content_read` decide which rows come back. **No scope rule is restated in TypeScript and no route filters on `tenant_id`.**
- **The grants are the narrowing.** `saas_runtime` holds column-only `SELECT` on eleven `invoice` columns, nine `content_item` columns and five `client` columns — with no table-level privilege on `invoice`, `content_item` or `client`, and no `INSERT`, `UPDATE` or `DELETE` on any of them. The invoice columns are the ones the route returns and nothing else; the columns the table also holds — the notes, the addresses, the import provenance, the timestamps, `tenant_id` — are outside the disclosure by grant rather than by a `select` a reviewer must trust.
- **Residual: `public.project` still carries the M0 table-level grant.** Two proofs in `tests/module-rls.test.ts` depend on that grant — the M0 module denial and the cross-tenant denial — failing on the restrictive policy rather than on a missing privilege, so narrowing it would change what those tests prove. The Work route therefore names only the columns it returns and never selects `source_system`, `source_id`, `import_batch_id`, `imported_at`, `budget_hours`, `manager_user_id` or `tenant_id`; the privilege is broader than the disclosure, and the gap is deferred to the Work write slice, which is where it can be closed without weakening a shipped proof.
- **Residual: `public.client` is platform-owned shared directory data.** It carries the permissive `tenant_isolation` policy and no module policy, exactly like `legal_entity` and `org_unit`, and the only five columns the runtime may read are `id`, `name`, `code`, `status` and `deleted_at`. Its exposure follows the route, and the only two routes that read a client name are module-gated: `GET /v1/work/projects` and `GET /v1/money/invoices`, each behind its own module's read permission. A member without Work or Money cannot reach a client name through either.
- **Residual: there is no write surface in any of the three modules.** No route creates, updates or deletes a project, an invoice or a content item; no permission names a write for them; and the runtime role holds no write privilege on `invoice` or `content_item` — the two new grants are column-only `SELECT`. `project` deliberately keeps its M0 table-level grant, which the residual above names, and there is still no write screen. The three screens offer no write control, so the client cannot offer a capability the server refuses.
- **Residual: `auditor` holds neither `money.read` nor `content.read`.** The role is built for aggregates and reconciliation, and this product builds neither, so it is refused an invoice list it would have nothing to reconcile against — the exclusion may be wrong, and it is asked as review question 16 rather than decided. The same question asks whether `hr` should read Content.
- **The reads leave no trail.** A successful module read writes no audit row, exactly as the People directory read does not: a read is not an export. That was already true for the directory and is now wider, because two of the three surfaces disclose money — a member can read an invoice list and the append-only table records nothing about it. The audit read surface does not exist either, so there is no way to review what was read even if it were recorded.
- Money is displayed as stored. Each amount is a `bigint` count of minor units with an explicit ISO currency on the row; the route selects it as `::text` and refuses a value outside `Number.isSafeInteger` with a sanitized `500 INTERNAL_ERROR` rather than rounding it, so no figure is ever rounded on the way to a screen. The screen shows the stored figure with its stored currency code, labels the tax column **Tax** — a stored amount, never a rate, never a jurisdiction-specific word — and computes nothing: no totals across rows, no currency conversion, no overdue calculation, no proration.
- The search is a literal `strpos(lower(col), lower($n)) > 0` and never `LIKE`, so `%` and `_` are data and cannot widen a match. A malformed `page` or `pageSize` is `400 INVALID_QUERY` before any query runs; every outcome, including the denials and the `400`, is `Cache-Control: no-store`; and no CSRF token is required, because all three are `GET`s.

## 6. Sensitive data

- Application-layer encryption for bank account numbers, tax identifiers and social-insurance identifiers, with a KMS-managed key and rotation.
- Only last-four values are stored in clear for display and matching.
- PII is redacted from logs, traces and error reports by default.
- Production data never enters development or test environments. Fixtures are synthetic.
- Document uploads are quarantined, scanned and served via short-lived signed URLs.
- The M0 People directory export is audited before disclosure, sent with `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and buffered nowhere server-side beyond the cursor batch. It has no signed URL, stored object, encryption-at-rest layer or time-limited link; those remain target controls for file exports.
- The M1 People directory page is a plain JSON read: it returns the seven granted identity columns on `person` (`id`, `employee_code`, `first_name`, `last_name`, `display_name`, `work_email`, `phone`), the two placement ids and the two names the server joins, never `tenant_id`, `user_id`, `personal_email`, `date_of_birth` or `gender`, excludes soft-deleted rows, and is sent `Cache-Control: no-store` on every outcome including denials and `400`s. It writes no audit row — a directory read is not an export — and the client renders each value as a React text node, with no `dangerouslySetInnerHTML`, no third-party script and nothing persisted to browser storage. There is no CSP yet (see §5), so that discipline is a code-review guarantee rather than a header-enforced one.
- The M1 People directory write path is the first route that stores member-entered text. It accepts only the six identity fields, each bounded by a length constant shared with the form's `maxLength`, and everything else a browser could send — `id`, `tenant_id`, `status`, `legal_entity_id`, `org_unit_id`, `user_id`, `deleted_at`, the timestamps, `personal_email`, `date_of_birth`, `gender` and the employment and statutory columns — is refused as `400 INVALID_BODY` before any query runs, because the route builds its column list from a closed map rather than from the body's keys. Values are used only as bound parameters; no SQL is assembled from user text. `display_name` is derived from the trimmed name parts when absent, so it cannot arrive as an arbitrary client claim, and it is stored and re-read from the database before it is returned. A rejection echoes no submitted value — `INVALID_BODY` carries no field names or contents, and a `409` for a taken employee code or work email names the collision without repeating the value, which would otherwise disclose another person's code or email to a member who is not entitled to read it. Success and denial responses are `Cache-Control: no-store`, nothing is written to browser storage, and the panel renders each value as a React text node with no `dangerouslySetInnerHTML`. Audit metadata records field names only, never old or new values, so a directory edit does not put PII into the append-only table. There is no delete or restore, so a member cannot destroy a directory row; last-write-wins means a concurrent edit overwrites silently, which is accepted for identity text and recorded in [ADR 0008](adr/0008-people-write-path.md) rather than papered over.
- The M1 People placement path is the first route that exposes organisation structure to a member. It discloses names — a legal entity's name and code and an org unit's name — that no other route had printed, and it discloses only the ones `app.person_placement_in_scope` already approved for that membership, so an entity-scoped HR member sees their own entity and its units, an org-unit-scoped member sees the subtree plus its parent as an unplaceable heading, and a member with nothing placeable gets an empty successful list rather than a denial that would confirm the tenant has entities. Reference rows are addressed by globally unique id with no `tenant_id` predicate; a cross-tenant id is unreachable because each reference table's `tenant_isolation` policy hides the row and the composite `(tenant_id, id)` foreign key from `person` makes storing it impossible, and the role holds no table-level or write privilege on either table. Both write routes read the row back rather than trusting the caller's payload, so a response always shows the stored pair, and a retired reference row surfaces a null name beside a still-stored id instead of a name that no longer exists. Placement carries no free text: the body is two UUIDs or nulls, validated against a closed contract, used only as bound parameters, and never echoed — `PLACEMENT_NOT_FOUND`, `PERSON_NOT_FOUND`, `SCOPE_DENIED` and `INVALID_BODY` each name a category and nothing else, so a probe cannot enumerate entities or units. The panel renders every value as a React text node, persists nothing beyond the theme, and disables save until the server's choices arrived, which keeps a member from submitting a placement they were never shown. What remains unmitigated is disclosure by placement itself: because scope keys on placement, moving a person decides who can see them, and the only evidence that happened is one `person.placement.changed` row and the directory the next member reads — there is no approval step, no undo and no placement history surface.
- The M1 People employment path moves date-and-status facts about a named colleague onto the same screen that already prints their name, code and work email. A history item is ten keys and nothing else — the employment id, the person id, the entity id and its joined name (null once the reference row is soft-deleted), the type, three dates, `noticeDays` and `status` — and it carries no jurisdiction, no source or import column, no timestamp and no compensation field, because `employment` has no compensation column to leak and the route names none outside that list. Dates leave the database as `to_char`'d `YYYY-MM-DD` strings so no timezone can shift a stored day on the wire, and every value is bound, never concatenated. A create or update stores no free text at all: the body is one enum, at most three calendar strings and one bounded integer, so the input surface the identity path opened — member-entered text rendered back to other members — is not widened here. All three outcomes are `Cache-Control: no-store`, including the `403`s and `404`s, the panel renders each value as a React text node with no `dangerouslySetInnerHTML`, and nothing is persisted to browser storage beyond the theme. Two gaps are documented rather than claimed closed: a history is **unpaginated and unbounded**, so one read prints a whole career to anyone with `people.read`, and there is **no employment-specific permission**, so a directory reader sees employment dates for every row they can see. Neither is reachable through the export, which still prints the same seven identity columns it always did and gains no employment column from this slice.
- The M1 People compensation read is the first route that discloses money, and it discloses a stored figure and nothing derived from it. A history item is seven keys — the compensation id, the person id, two `to_char`'d `YYYY-MM-DD` strings, `ctcMinor`, `currency` and `payFrequency` — and the runtime role cannot read the other eight columns of the table at all, so `structure` (the `jsonb` a future salary breakdown would live in), the import-provenance trio, `imported_at`, both timestamps and `tenant_id` are outside the disclosure by grant, not by a `select` the reviewer must trust. There is no aggregate, no comparison, no sorting by amount and no cross-person list: one id in, that one person's rows out, inside the same scope the directory already applies. Conversion is refused rather than performed — a `ctc_minor` outside `Number.isSafeInteger` answers a sanitized 500 with no amount in the body, so no figure is ever rounded on the way to a screen — and the amount, currency and frequency stay three separate values because nothing in this build knows how they relate: no monthly or annual figure is computed, labelled or displayed, and the only arithmetic is a thousands-grouping helper that assumes two fractional digits because the table records no decimal exponent. `currency` is `char(3)` with no `CHECK`, so an operator-written code prints as stored; that is a data-quality gap the money slice owns. The read is unpaginated and unbounded like the employment history, is `Cache-Control: no-store` on every outcome, writes no audit row on success, reaches no file because the export gained no column, and is invisible to a browser unless the member's role holds `people.compensation.read` — at which point the screen shows the panel, and shows nothing at all when it does not.
- The M1 People compensation write is the first route that stores money, and it stores a figure the caller typed and nothing computed from it. Both routes are gated on `people.compensation.write` — a published permission held by `owner`, `admin`, `hr` and `finance` — so `manager`, `auditor` and `employee` are refused at the gate before any query runs, and the refusal is one `authorization.denied` row naming `people.compensation.write` and the route template with no person id, amount or currency in its metadata. The order is fixed and it is the disclosure rule: UUID guards, the directory read under `app.person_visible`, `select app.person_in_scope($1)`, then the body. A member who may not maintain this colleague is refused before their payload is parsed, so a probe cannot learn which key names a valid salary row takes, and a member who may gets a `400` they can act on. `403 SCOPE_DENIED` is observable only where the read oracle is wider than the write oracle — a linked member's own directory row, which `app.person_visible` opens and `app.person_in_scope` never does; everyone else is not visible at all and gets the uniform `404 PERSON_NOT_FOUND`, and on a patch a row the caller cannot even read is `404 COMPENSATION_NOT_FOUND`, so no compensation id is probeable through this path.
- The write surface is five columns and one closed key set: `effectiveFrom`, `effectiveTo`, `ctcMinor`, `currency`, `payFrequency`. Nothing else is settable, and the database agrees: `person_id` and `tenant_id` are insertable but not updatable, so re-parenting a salary row across the directory is refused by the grant before `compensation.scope_update`'s `WITH CHECK` is reached — the column grant is the first line and the policy the second. Money stays minor units: `ctcMinor` must be a `Number.isSafeInteger` between `0` and `Number.MAX_SAFE_INTEGER`, never rounded and never a float, so an out-of-range figure is a `400` rather than a silently converted value; `currency` must be exactly three ASCII `A-Z` characters and is never upper-cased, because the read prints what was stored and folding would invent a code the operator did not write; dates must be real `YYYY-MM-DD` calendar days and `effectiveTo` must be at or after the merged `effectiveFrom`. A patch merges absent keys onto the stored row, so a member can state one field without restating five, and the merged row — not the patch — is what the bounds are checked against.
- No DML statement uses `RETURNING`: the id comes from `node:crypto`'s `randomUUID()`, the statement names its columns, and the answer is a read-back through the same `COMPENSATION_SELECT` and `COMPENSATION_FROM` fragments the list uses, so a write response and a list response cannot diverge in date formatting or bigint handling. That is a convention on this table, not a necessity — the compensation policies key on `person_id`, which names an already-existing person, so `INSERT ... RETURNING` would have worked, and `tests/people-compensation-write.test.ts` probes exactly that and pins the difference from `person`, where 0008's `scope_read` reads the new row's own id and refuses it. A patch that moves nothing sends no `UPDATE` and writes no audit row and answers with the stored row; a `23505` on `unique (tenant_id, person_id, effective_from)` — on either command — is one `409 COMPENSATION_PERIOD_EXISTS` that names the collided day without repeating the amount. There is no overlap rule beyond that key, no delete route, no `DELETE` grant and no delete policy: a wrong figure is amended in place, and the amendment keeps no previous value. Audit metadata is `{ fields: [...] }` and nothing else, so the append-only table never accumulates a salary — which is also the residual, because with no before or after recorded the trail cannot show what a corrected figure used to be. Every outcome is `Cache-Control: no-store`, the panel renders each value as a React text node with no `dangerouslySetInnerHTML`, nothing is persisted to browser storage, and the export still prints the same seven identity columns it always did.
- The M1 Work, Money and Content read surfaces disclose three module-shaped sets of facts and nothing derived from any of them. An invoice row is twelve keys — the invoice id, number, client id and name, status, two `to_char`'d dates, the currency, and four amounts — and the runtime role cannot read any other column of `invoice` at all, so the notes, the addresses, the import provenance, the timestamps and `tenant_id` are outside the disclosure by grant rather than by a `select` a reviewer must trust. A project row is ten keys and a content row is nine, with the same property. Two of the three surfaces carry money, and the money rules are the same ones the compensation read adopted: each amount is a `bigint` count of minor units with an explicit ISO currency on the row, selected as `::text`, and a value outside `Number.isSafeInteger` is refused with a sanitized `500` rather than rounded, so no figure is ever rounded on the way to a screen. Nothing is computed from the figures — no total across a page, no currency conversion, no overdue calculation, no proration, no tax rate — and the tax column is a stored amount labelled **Tax**, never a jurisdiction-specific word. A client name is disclosed by the Work and Money screens, and `client` is platform-owned shared directory data: the runtime may read only `id`, `name`, `code`, `status` and `deleted_at` on it, the table carries only the permissive `tenant_isolation` policy, and both routes that read a name are module-gated. Every outcome of the three routes is `Cache-Control: no-store`, every value is a bound parameter or a `to_char`'d string, the screens render each value as a React text node with no `dangerouslySetInnerHTML`, and nothing is persisted to browser storage beyond the theme. **A successful read writes no audit row**, so an invoice list that was read leaves no trail in the append-only table — the same gap the directory read has, now covering money.

## 7. Audit

- Append-only `audit_event` table; updates and deletes are blocked by trigger for the owner and tenant roles alike.
- The runtime role has `INSERT` only on `audit_event`; it has no `SELECT`, `UPDATE` or `DELETE`. `appendAuditEvent` takes the tenant from `app.tenant_id`, never from a caller argument, uses parameters and has no `RETURNING`.
- Captured in M0: tenant provisioning, entitlement grant and cancellation, authenticated access denials, and People directory exports. Authentication, role changes, payroll, bank changes, connector credentials, document downloads and tenant settings are target events, not yet implemented; other export paths do not exist.
- Added with the M1 scope path (§5.1), outside the M0 set: `person.user.linked`, `person.user.unlinked` and `membership.scope.changed`, each written in the same transaction as the change, with before/after limited to `user_id` or the sorted `{ scope_type, id }` set — no names, emails or labels.
- Added with the M1 People write path (§2), also outside the M0 set: `person.created` and `person.updated`, actor type `user`, entity type `person` and the person's own id as entity ID. Metadata is `{ module: 'people', fields | changedFields }` — the sorted set of identity field names written — with no previous or new values, so the append-only table does not accumulate the directory's own PII. The row is appended in the same member transaction as the write, so an audit insert failure rolls the write back and the caller gets a sanitized 500; a create that 400, 403 or 404s, and a PATCH where nothing changed, write nothing. Because that path is a member transaction, the person id is generated by the API before the insert and used as the entity ID after the read-back succeeds. `tests/people-write.test.ts` asserts the exact row, including the fail-closed case driven by a revoked audit grant.
- Added with the M1 People placement path (§2), also outside the M0 set: `person.placement.changed`, actor type `user`, entity type `person` and the person's own id as entity ID. Metadata is `{ module, legalEntityId, orgUnitId, previousLegalEntityId, previousOrgUnitId }` — after and before, ids only, never a name, code, email or any other person value. It is the first People audit row that names objects rather than field names, because a placement is the one directory change that alters which colleagues can read the row, so the pair before and the pair after are the facts an auditor needs and a field-name list would be useless; the ids are not PII and carry no tenant or personal content. It is appended in the same member transaction as the update, so a revoked audit grant rolls the placement back to a sanitized 500 with the stored pair unmoved, which `tests/people-placement.test.ts` proves. A no-op placement writes no row, and the `404`, `403 SCOPE_DENIED` and `400` refusals write none.
- Added with the M1 People employment path (§2), also outside the M0 set: `employment.created` and `employment.updated`, actor type `user`, entity type `employment` and the **employment row's own id** as entity ID — the first People audit row keyed to a child record rather than to the person, because the object that changed is the employment, not the directory entry. Metadata is `{ module: 'people', fields | changedFields }`: the sorted set of employment field names written, never a date, a notice period or a status, so the append-only table does not accumulate employment history alongside the row it describes. It is appended in the same member transaction as the write, so a revoked audit grant rolls the write back to a sanitized 500 with the row unmoved, which `tests/people-employment.test.ts` proves; a `400`, `403`, `404` or `409` refusal and a patch that names nothing different write no row, and a successful history read writes none either.
- Added with the M1 People compensation write path (§2), also outside the M0 set: `compensation.created` and `compensation.updated`, actor type `user`, entity type `compensation` and the **compensation row's own id** as entity ID — the second People audit row keyed to a child record rather than to the person, for the employment path's reason: the object that changed is the pay row. Metadata is `{ fields: [...] }` on both, never `{ module, ... }`: the sorted names written on a create and the names that actually moved on an update, with no amount, currency, date or frequency, and no before or after value of any kind. That makes it the one People write row whose metadata omits `module`, which [ADR 0012](adr/0012-compensation-write.md) decision 11 records as the key set this slice was specified to write rather than papering over the inconsistency. It is appended in the same member transaction as the write, so a revoked audit grant rolls the insert or the update back to a sanitized 500 with the row unmoved, which `tests/people-compensation-write.test.ts` proves; a `400`, `403`, `404` or `409` refusal and a patch that changes nothing write no row, and a successful history read writes none either.
- Three refusals on the People write, placement, employment and compensation paths are deliberately not audited: `SCOPE_DENIED` (the both-null unplace, a tenant-wide-only create, an employment create or update on a person the write oracle refuses, or a compensation create or update on a person `app.person_in_scope` refuses) and the uniform `404 PERSON_NOT_FOUND`, `404 PLACEMENT_NOT_FOUND`, `404 EMPLOYMENT_NOT_FOUND` and `404 COMPENSATION_NOT_FOUND`. The employment history `GET` and the compensation history `GET` write no audit row at all — a read of a colleague's dates, or of their pay, is not an export — and `tests/people-employment.test.ts` pins that a successful list leaves the tenant's audit count unchanged, as `tests/people-compensation.test.ts` pins the same for an owner reading two stored rows.
- **The M1 module reads write no audit row either, and that is now a money-sized gap.** `GET /v1/work/projects`, `GET /v1/money/invoices` and `GET /v1/content/items` are reads, not exports, so a successful one appends nothing — and `tests/work.test.ts`, `tests/money.test.ts` and `tests/content.test.ts` each pin that the tenant's audit count is unchanged after a successful list. The denial side still audits: an unentitled tenant or a role without the permission produces the same `authorization.denied` row as every other gated route, with `reason`, `module`, `operation`, `permission`, `method` and `path`. What is missing is the read itself: a member who opens an invoice list leaves no record that they did, and there is no audit read surface either, so the trail cannot be reviewed even for the events that are recorded. This is a documented residual on threat row T45 and an accepted gap for this batch, not a claim that reads are audited.
- The first refusal is decided by a database policy or a helper the member cannot influence, and every 404 is indistinguishable from "not in your tenant" on purpose — recording any of them would mean writing a row that names the existence and the tenant of a person, legal entity or org unit the actor is not entitled to see, which is exactly what the narrowing exists to prevent. Role and entitlement denials on these routes do audit as `authorization.denied`, like every other gated route.
- An authenticated access denial is one `authorization.denied` row with `entity_type = 'request'`, no entity ID, actor type `user` and the session's user, IP and user agent. Metadata carries `reason`, `method` and the registered route `path`; `module` and `operation` are added when known, and `permission` only for a role denial. Reasons are exactly `MEMBERSHIP_DENIED`, `PLATFORM_ACCESS_DENIED`, `MODULE_NOT_ENTITLED` and `ROLE_DENIED`. A compensation refusal is the fullest example: its metadata is those six keys and no more — `reason`, `module`, `operation`, `permission`, `method`, `path` — naming `people.compensation.read` and the `/v1/people/:id/compensations` template while carrying no person id, no amount and no currency, which `tests/people-compensation.test.ts` asserts by key set rather than by subset because the point of the row is what is absent from it; a compensation *write* refusal is the same shape with `people.compensation.write` and the create or patch template in the two value slots, pinned the same way by `tests/people-compensation-write.test.ts`. The denial-path validator was fixed in the same slice that added the read: it now checks a permission name against the published `PERMISSIONS` list instead of a one-dot pattern, because `people.compensation.read` and `people.compensation.write` each have two dots, and under the old pattern the validation threw *inside* `recordAccessDenial`, whose failure the denial path logs and swallows — so a role denied the compensation read produced the correct HTTP answer and no audit row at all until T22 found it and its test began counting rows.
- The denial path uses the route template, never the raw URL, and metadata excludes role, email, tenant slug, headers, cookies, tokens, query strings, request bodies and stack traces. Unauthenticated requests, unknown errors, CSRF/Origin failures and rate-limit rejections are not access denials and are not audited by this path.
- Denial audit is best-effort: it opens its own runtime transaction because platform access or membership may be exactly what failed, so it cannot reuse the check it is recording. If the audit insert fails, the failure is logged and the original denial response is still returned. This is deliberately different from privileged business actions, where an audit write failure rolls back the action; that rollback is tested for an employment insert.
- A People directory export writes one `people.directory.exported` row with entity type `tenant`, the session tenant ID and actor user, plus the request IP and user agent. Metadata is limited to module, format and the exported column names; it carries no row count, query string, header, cookie, token, email address or person data. The row is committed in its own member transaction, under the same People read gate, before response headers or CSV bytes are sent. If that audit write fails, the export is refused with a sanitized 500 and no download. The streaming transaction rechecks the gate so an entitlement change between the two transactions is still denied; it writes no second event.
- Audit events include actor, action, entity, before/after where appropriate, IP, user agent and timestamp.
- Audit retention is defined per jurisdiction; legal holds are explicit.
- Audit logs are not editable by tenant admins. An audit read API and UI are not built.

- Private networking; database and object storage not publicly reachable.
- Encryption in transit (TLS 1.2+) and at rest.
- Least-privilege infrastructure roles; no long-lived production credentials in CI.
- Secrets in a managed store with rotation; never in Git.
- Backups encrypted, tested with scheduled restore drills. Not built in M0. ## 9. Privacy and compliance

- GDPR-aligned DPA baseline, with local-law addenda where required (including DPDP for customers it applies to). The applicable privacy schedule is named in the contract, not assumed from the customer's location.
- Purpose limitation: customer data is used to provide the service, not to train models or build a cross-customer dataset.
- Subprocessor register published to customers; new subprocessors notified before use.
- Retention and deletion schedules per record class, with legal-hold exceptions.
- Data subject requests supported through the customer's administrator and the studio.
- Breach notification runbook with defined owners and timelines.
- Customer data is exportable in CSV/JSON plus original documents. Target; M0 provides only the scoped People directory identity CSV, not the full export or original documents.

## 10. AI policy

- No customer payroll, bank or statutory data is sent to consumer AI services.
- Any AI feature uses an enterprise/zero-retention endpoint or a self-hosted model, under a documented data flow.
- AI may assist with drafting, search, summarisation and anomaly hints. It does not calculate statutory liability, approve payroll or decide access.
- AI output is labelled, reviewable and never silently applied to a financial record.
- Prompts and outputs containing customer data are not retained for model training.

## 12. Incident response

1. Triage and classify severity; appoint an incident lead.
2. Contain: revoke sessions/keys, isolate tenants or components.
3. Preserve evidence; do not destroy logs.
4. Notify the affected customer and regulator within contractual and legal timelines.
5. Remediate the root cause and add a regression test.
6. Publish an internal post-incident review; share the relevant parts with the customer.

Severity 1 means confirmed or suspected cross-tenant access, entitlement bypass into restricted module data, payroll corruption, or exposure of restricted data. It pages the on-call owner immediately.
