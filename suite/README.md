## First slice

**People + Switch.** HRIS and payroll with jurisdiction packs for 50–500 person service businesses, with a migration console that imports history, rehearses it, reconciles totals and only then promotes to production. The core does not assume a country; each legal entity selects its jurisdiction, currency, locale and timezone.

The product is an **organisation workspace with independently licensable modules**. Every tenant gets the platform core: organisation, legal entities, memberships, roles, audit, documents, search and export. A customer may license one module, several, or the full suite. The module catalog and entitlement model ship with the first slice, so adding CRM, Work, Money or Content later is a configuration change on the same schema — not a data migration or a second edition.

## Non-negotiable rules

1. **Tenant isolation is a database property.** Every tenant business table carries `tenant_id`, has RLS enabled and has a `tenant_isolation` policy; cross-tenant references are blocked by composite foreign keys. The identity tables `auth_session` and `invitation` are the only exceptions: they carry `tenant_id` but deliberately have no RLS, the runtime role has no privilege on either, and they are reached only through security-definer auth functions.
2. **Module access is an entitlement, checked on the server.** A licensed module is not a UI flag. Every module request resolves entitlement + role + scope in that order; M0 implements the first two, and M1's `0012_people_scope.sql` puts the third in the database as restrictive RLS policies rather than in the request layer — so a query that forgets a scope predicate cannot return out-of-scope rows, and only a transaction that set `app.user_id` is narrowed — which is how `GET /v1/people`, the directory export, both People identity write routes, both placement routes and the three employment-history routes are narrowed today, with no scope predicate in application code — the placement routes ask `app.person_placement_in_scope` for their answers rather than restating the rule, and each employment write asks `app.person_in_scope` — the write oracle, which gives an employee no self exception — while the history read is narrowed only by `app.person_visible`, so reading a colleague's employment is not the same decision as changing it. The database helpers `app.has_module_read('<code>')` and `app.has_module_write('<code>')` enforce tenancy and entitlement, not role; they are the second line of defence. `app.has_active_module('<code>')` remains as a compatibility delegate to the write helper.
3. **One shared directory.** Person and client identity live in the platform. Modules extend those records; none creates a parallel employee or client table.
4. **Money is integer minor units.** `bigint` plus currency. No floating point in payroll or billing.
5. **Payroll history is append-only.** Finalised runs are reversed, never edited. Audit events cannot be updated or deleted.
6. **Imports never write production directly.** Rows land in staging, carry provenance, and are promoted transactionally.
7. **No statutory rule is invented by a model.** Contribution, withholding and statutory-reporting rules are versioned data per jurisdiction, reviewed by a qualified local advisor and proven with golden test cases.
8. **Every portability export is complete.** When full data export ships, a tenant must be able to leave with its records and documents in open formats, module by module, and cancelling a module never destroys the data. The M0 `GET /v1/people/export` route is a scoped directory identity CSV, not that portability feature.

## Database

Target: PostgreSQL 16+ (17 recommended), `pgcrypto` and `citext`, in the data region selected for the tenant at provisioning.

```bash
pnpm db:bootstrap   # roles and database, once
pnpm db:migrate     # checksummed migrations; reapplies runtime and auth grants
pnpm db:seed        # idempotent module catalog
pnpm db:provision --name "Synthetic Co" --slug synthetic-co --region test-region \
  --owner-email owner@example.test --owner-name "Synthetic Owner" --module people
pnpm db:invite --tenant synthetic-co --email owner@example.test
# owner-only scope authoring (0012): needs an accepted invitation (active owner) and directory rows,
# so the freshly provisioned synthetic tenant above refuses it until a person and a member exist
pnpm db:scope link --tenant synthetic-co --person EMP001 --user staff@example.test --actor owner@example.test
pnpm db:scope set  --tenant synthetic-co --user manager@example.test --actor owner@example.test --org-unit <uuid>
pnpm db:scope show --tenant synthetic-co --user manager@example.test
```

The module catalog is reference data, seeded once and updated by migration. A tenant is then granted entitlements; the catalog itself is not writable by the runtime role. Provisioning, entitlement changes and scope authoring run through owner-only libraries on `DB_OWNER_URL` and audit in the same transaction; none of them is reachable from the API. `db:scope` prints ids and labels only, never a token or a connection string, and refuses any actor without an active `owner` membership in that tenant. See [`db/README.md`](db/README.md).

The migrations and seed are applied by the repository harness against a real local PostgreSQL 17 instance, with fresh-apply, checksum, role-privilege, access-helper, RLS policy, people-scope, scope-administration, membership, provisioning, audit, authentication, People-directory-export, People-directory read-path, People-directory write-path, People-placement, People-employment, People-compensation, People-compensation-write, Work-read, Money-read, Content-read, CRM-account-read, CRM-account-write, CRM-contacts and schema-inventory suites. The web unit tests and eight Playwright browser journeys in three spec files run locally; they share one disposable database and run the built client through Vite preview with an in-process API, serially, so the read-only journey depends on the rows the first one created. `scripts/secret-scan.ts` scans tracked and untracked non-ignored regular files (not history, ignored files, packed objects or remote state), and `pnpm audit --prod --audit-level high` checks production dependencies. The CI workflow at the repository root declares a PostgreSQL 16/17 matrix and the browser job, but no job has executed a step: the GitHub remote exists, and the account is annotated as locked for billing, so PostgreSQL 16 and CI browser execution are unproven. A restore drill is still required before real data. See `db/README.md`, `docs/release/m0-evidence.md` and `docs/roadmap.md`.

The application connects as a role that does **not** own the tables. Tenant and user context are set per transaction:

```sql
set local app.tenant_id = '<tenant-uuid>';
set local app.user_id = '<user-uuid>';
```

RLS denies all rows when the tenant setting is absent. Request routes resolve membership through `withMemberTransaction`; the worker uses the system-only `withTenantTransaction`. Identity lookups and session storage use a separate `saas_auth` role that never sees tenant business data. Tenant provisioning and invitation creation are owner-only and never reachable from the API.

## Application skeleton

`apps/api` and `apps/worker` contain the first request layer. `POST /v1/auth/login` verifies an email and password with Argon2id, resolves the tenant by slug through the auth role, and issues an opaque `saas_session` cookie plus a CSRF token. Identity is global (`app_user.email` is unique) and memberships are per tenant, so the same password signs a user in to each tenant it belongs to. `POST /v1/auth/invitations/accept` consumes a one-time invitation, activates the invited membership and signs the user in; a first-time invitee sets a password, while an active user invited to a second tenant verifies its existing one. Protected routes read the session cookie only, verify the hashed session server-side, then call `withMemberTransaction` from `@saasmodels/db` with the session's tenant and user: both IDs are validated, the active membership role resolves first, then platform access, the module entitlement and the role permission run through the runtime role, and the caller's query runs in the same transaction. The context route returns the resolved role, its canonical permissions and only the modules effective under both entitlement and role, each with its catalog name and sort order, and is sent `Cache-Control: no-store`. State-changing requests require an exact Origin match, logout and the seven state-changing People routes — create, identity update, placement update, employment create and update, compensation create and compensation update — require the session CSRF token while the placement options `GET` does not, login is rate-limited per source address and per email, and every `/v1/auth/*` response is `Cache-Control: no-store`. The worker exports `runTenantJob` on the system-only `withTenantTransaction` without a queue or polling loop.

`GET /v1/people/export` is the first production module route and is available without proof-route enablement. It is gated by `withMemberTransaction` with `{ module: 'people', operation: 'read' }`, streams the seven identity fields `person_id`, `employee_code`, `first_name`, `last_name`, `display_name`, `work_email` and `phone` from a server-side cursor in batches, and commits a `people.directory.exported` audit row before the first byte. Tenant scope is RLS; no `tenant_id` filter is passed, and query or header overrides are ignored. Since 0012 the same transaction also sets `app.user_id`, so a scoped member's export is narrowed by the restrictive policies; the CSV carries no scope label. The runtime role has column-level `SELECT` on those fields plus `deleted_at` and the two placement ids — the export reads only the seven — and no table-level `SELECT` on `person`. CSV output is RFC 4180 with CRLF and formula-prefix mitigation; the response is `text/csv; charset=utf-8` with `no-store`, `nosniff` and no `Content-Length`.

`GET /v1/people` is the first route to read the directory for a screen. It is gated the same way and returns exactly the `PeopleListResponse` contract — `items` of the seven directory identity fields plus `legalEntityId`, `legalEntityName`, `orgUnitId` and `orgUnitName`, a JSON-number `total`, and the effective `page` and `pageSize` — ordered by `lower(display_name), id` so paging is deterministic. `q` is a trimmed, literal, case-insensitive substring over `display_name`, `employee_code` and `work_email` through `strpos(lower(...), lower($n))`, so `%` and `_` are data, not wildcards, and no SQL is built dynamically. `page` defaults to 1 and `pageSize` to 20 with a 50 ceiling; a repeated, non-integer, out-of-range or over-length parameter is a `400 INVALID_QUERY` before any query runs, and a page past the end returns an empty `items` array with the true `total`. Scope narrowing is left entirely to RLS: the route sets no scope predicate in SQL or TypeScript. Every response, including denials and `400`s, is `Cache-Control: no-store`, and a successful read writes no audit row.

`POST /v1/people` and `PATCH /v1/people/:id` are the first routes that change stored data, and they are gated by `withMemberTransaction` with `{ module: 'people', operation: 'write' }`, so `people.write` is required before the body is parsed — a malformed body from a role that cannot write is a `ROLE_DENIED`, not a `400`. Both first require a valid session and a matching `x-csrf-token`, checked with the same timing-safe comparison as logout, and the `onRequest` origin hook still refuses another origin ahead of them. Both accept only the six identity fields — `firstName`, `lastName`, `displayName`, `employeeCode`, `workEmail`, `phone` — through the closed `PeopleCreateInput` / `PeopleUpdateInput` contracts in `packages/contracts/src/people.ts`, and build their column list from a server-side map, so any other key, including `id`, `tenantId`, `status`, `legalEntityId`, `orgUnitId`, `userId`, `deletedAt`, `personalEmail` and `dateOfBirth`, is a `400 INVALID_BODY` with nothing echoed. Create requires a non-empty first name, derives `displayName` from the trimmed names when absent, and refuses a new unplaced person for a member who has scope rows with `403 SCOPE_DENIED`, because a fresh record has no placement for `scope_insert` to approve. The API generates the person UUID; the insert carries `id` and `tenant_id` (from `app.current_tenant_id()`) and **no `RETURNING`** — the restrictive `scope_read` policy cannot observe a row the same command created, so `INSERT ... RETURNING` fails `42501` — and the route then reads the directory row back inside the same transaction, answers `201`, and fails closed with the sanitized `500` if that read returns nothing. Update reads the row first, writes only the columns whose effective value differs, returns the stored row with no `UPDATE` and no audit when nothing changed, and answers one uniform `404 PERSON_NOT_FOUND` for an unknown, malformed, cross-tenant, soft-deleted or out-of-scope id. A `23505` becomes `PERSON_CODE_TAKEN`, `PERSON_EMAIL_TAKEN` or `PERSON_CONFLICT` on either route, without repeating the value. `person.created` / `person.updated` are appended in the same transaction with sorted field names only in metadata, and an audit failure rolls the write back to a sanitized `500`. Concurrent edits are last-write-wins; there is no version column, no delete, no restore and no status change. `saas_runtime` holds 10 `SELECT`, 8 `INSERT` and 8 `UPDATE` column privileges on `person` (26 in total: `id` insertable but not updatable, `legal_entity_id` and `org_unit_id` selectable and updatable but not insertable), no table-level privilege and no `DELETE`. Every response is `Cache-Control: no-store`; scope and role denials audit as `authorization.denied`, a `SCOPE_DENIED` or a `404` does not. See [ADR 0008](docs/adr/0008-people-write-path.md).

`GET /v1/people/placement-options` and `PATCH /v1/people/:id/placement` are the placement path, and both sit behind `{ module: 'people', operation: 'write' }` — including the `GET`, because a member who cannot place anybody has no reason to read the org structure. The patch body is the closed `PeoplePlacementInput`: exactly `legalEntityId` and `orgUnitId`, each a UUID or `null`, always the whole statement, so there is no omit-to-keep and a unit named with a null entity is refused before any query. Session, exact Origin and the CSRF token come first; the `GET` needs no token. Every scope answer comes from `app.person_placement_in_scope(legal_entity_id, org_unit_id)` — the same security-definer helper `scope_insert` and `scope_update` call — asked four times for the options (`canUnplace` is the both-null call, an entity's `placeable` flag the entity-only call, a unit only when its own pair is approved, and an entity is also listed when it owns a placeable unit) and once for the write; no scope rule is restated in SQL or TypeScript. The patch also checks that the named unit's `legal_entity_id` equals the named entity, because `person` carries a composite foreign key to each reference table but nothing ties the pair together. Unreachable targets stay hidden: an unknown, soft-deleted, cross-tenant, out-of-scope or wrong-entity reference is `404 PLACEMENT_NOT_FOUND`, an unknown, malformed, soft-deleted, cross-tenant or out-of-scope person is `404 PERSON_NOT_FOUND`, and only the both-null unplace — which has no id to hide and which only a tenant-wide member may do — is `403 SCOPE_DENIED`. The response is the same eleven-key directory item the list returns, read back inside the transaction after the write: `UPDATE ... RETURNING` cannot carry a joined name, so both write routes now read back, and a `rowCount` other than one is the sanitized `500`. An unchanged placement sends no `UPDATE` and writes no audit row; a change appends `person.placement.changed` with `{ module, legalEntityId, orgUnitId, previousLegalEntityId, previousOrgUnitId }` — ids only, and the previous pair recorded because a placement is the one directory change that moves which colleagues can see the row. Reading the names needed column-only `SELECT` on `legal_entity (id, name, code, deleted_at)` and `org_unit (id, name, legal_entity_id, deleted_at)`, eight privileges with no table-level grant, no write and no `tenant_id` grant on either; cross-tenant references are unreachable twice over, through the reference table's own `tenant_isolation` policy and the composite foreign key. The runtime table-grant allowlist is unchanged at twelve rows. Placement is a directory attribute, not an employment record, and the CSV export still emits the seven identity columns — the divergence is recorded in [ADR 0009](docs/adr/0009-people-placement.md) rather than quietly closed.

`GET /v1/people/:id/employments`, `POST /v1/people/:id/employments` and `PATCH /v1/people/:id/employments/:employmentId` are the employment history path, and they are the first product routes to write `employment`. The read and the writes are deliberately decided by different oracles: the `GET` sits behind `{ module: 'people', operation: 'read' }` and contains no scope statement at all, because `employment`'s restrictive `scope_read` calls `app.person_visible(person_id)` — the same read helper `person`'s policy uses, and the one that carries the linked-employee self exception — while each write sits behind `operation: 'write'` and selects `app.person_in_scope(person_id)` inside the member transaction before any DML. That pre-check is not a duplicate of the policy: `saas_runtime` holds whole-table `INSERT`, `UPDATE` and `DELETE` on `employment` from the M0 proof surface, so without it a refused create raised `42501` and a refused update matched zero rows, and the caller received a sanitized `500` for what is a scope decision; asking the helper first answers a typed `403 SCOPE_DENIED`, and because the two helpers differ in exactly one respect — an employee is never writable-through — one membership can be shown "you may read this" and "you may not maintain this" at the same time. A create accepts `employmentType` and `startDate` plus the optional `endDate`, `probationEndDate` and `noticeDays`; a patch may additionally name `status`, and an absent key means unchanged while an explicit `null` clears only those three optionals. There is no `personId` in the body, because the path supplies it, and no `legalEntityId`: the entity is copied from `person.legal_entity_id` at the moment of the write, so an unplaced person or one placed on a retired entity is `409 EMPLOYMENT_ENTITY_REQUIRED` and the row keeps the entity it was created against after the person moves elsewhere. `status` is absent from the insert column list, so a new row is `active` because the column default says so and not because a caller said so, and `work_jurisdiction_id`, `source_system`, `source_id`, `import_batch_id` and the timestamps are named by no statement. Dates are `YYYY-MM-DD` strings checked for shape and for being a real day, an end or probation date cannot precede the start, `ended` requires an end date, `notice_days` is an integer from 0 to `EMPLOYMENT_NOTICE_DAYS_MAX`, and a status moves only forward — `active` to `ended` or `cancelled`, never back, and re-naming the stored status is a no-op that writes neither row nor event. Existence stays hidden: an unknown, malformed, soft-deleted, cross-tenant or out-of-scope person id — and an entity id or the person's own employment id used where a person id belongs — is the same `404 PERSON_NOT_FOUND` the identity and placement routes give, and an employment id that is not a row of that person is `404 EMPLOYMENT_NOT_FOUND`. Both writes require session, exact Origin and the CSRF token; the `GET` needs neither. A successful write appends `employment.created` or `employment.updated` in the same transaction with the employment row's own id as entity ID and sorted field names only in metadata, so a revoked audit grant rolls the write back to a sanitized `500`, and every response on all three routes is `Cache-Control: no-store`. The list is unpaginated and unbounded — every row for one person, newest first, `total` its length — which is a recorded limit, not a design, because the Switch import is the first path that will make a person hold many rows. The slice adds no migration, no policy, no helper, no grant and no schema change; the runtime table-grant allowlist is still twelve rows, `person` still has its 26 column privileges, and the export still emits the same seven identity columns with no employment column in them. ADR [0010](docs/adr/0010-people-employment.md) records the read-versus-write-predicate decision and the rejected alternatives.

`GET /v1/people/:id/compensations` is the compensation history path, and it is the first route behind a permission the module's own read does not imply. It sits behind `{ module: 'people', operation: 'read', permission: 'people.compensation.read' }` — a new optional field on the gate that replaces only the permission the role question asks, so entitlement is still checked first against `people`/`read` and `MODULE_OPERATIONS` stays `read`/`write`. `owner`, `admin`, `hr` and `finance` hold `people.compensation.read`; `manager`, `auditor` and `employee` do not, and the refusal arrives as `ROLE_DENIED` naming that permission before the person id is read, so the route cannot probe whether a colleague has a salary row. `0013_compensation_read.sql` adds one `AS RESTRICTIVE` policy — `scope_read` on `compensation`, `using (app.person_visible(person_id))`, the ninth scope policy and the first on a third table — and `runtime-grants.sql` adds exactly seven column `SELECT` privileges (`id`, `person_id`, `effective_from`, `effective_to`, `ctc_minor`, `currency`, `pay_frequency`) with no table-level grant and no DML, which is the whole grant change in the slice; the two had to land together because `tests/scope.test.ts` derives the runtime-readable `person_id` tables from the catalog and requires that read policy on each. The route states no scope predicate, answers one `404 PERSON_NOT_FOUND`, returns `{ items, total }` ordered `effective_from desc` unpaginated and `no-store`, writes no audit row on success, and refuses a `bigint` outside `Number.isSafeInteger` as `INTERNAL_ERROR` rather than rounding it. As that slice was written there was no compensation write anywhere — no permission name, no route, no grant and no write policy; the write half is the next paragraph and ADR [0011](docs/adr/0011-compensation-read.md) records the permission-before-id order, the gate override and the rejected alternatives.

`POST /v1/people/:id/compensations` and `PATCH /v1/people/:id/compensations/:compensationId` are the write half, and they sit behind `{ module: 'people', operation: 'write', permission: 'people.compensation.write' }` — the sixth published permission, held by `owner`, `admin`, `hr` and `finance` and refused to `manager`, `auditor` and `employee`, and held by finance without `people.write`, because a pay row touches `compensation` alone. Both require session, exact Origin and the CSRF token, and both decide the person and the scope before the body: the UUID guard, then the directory select under `app.person_visible` as the visibility test (`404 PERSON_NOT_FOUND`), then `select app.person_in_scope($1)` — the write oracle, so a linked employee who can read their own row still gets `403 SCOPE_DENIED` rather than a silent policy refusal — and only then the parse. `0014_compensation_write.sql` adds exactly two `AS RESTRICTIVE` policies, `scope_insert` with `check (app.person_in_scope(person_id))` and `scope_update` with the same expression as both `using` and `with check`, and no delete policy; `runtime-grants.sql` takes the runtime from seven column `SELECT` privileges to 20 privileges over eight columns — `INSERT` on `id`, `tenant_id`, `person_id` and the five write columns, `UPDATE` on the five (`effective_from`, `effective_to`, `ctc_minor`, `currency`, `pay_frequency`) — with no table-level privilege and no `DELETE`, so a re-parenting update and a delete are both `42501` from the grant before the policy is consulted. A create is the closed five-key `CompensationCreateInput`; a patch is `CompensationUpdateInput` over the same five, where an absent key keeps the stored value, only `effectiveTo` may be stated as `null`, and the merged row is what validation sees — a patch that moves nothing writes neither row nor event. `ctcMinor` is an integer from 0 to `Number.MAX_SAFE_INTEGER` and never rounded, `currency` is exactly three ASCII `A–Z` and never upper-cased for the caller, a date must be shaped and real, and an end cannot precede the merged start; anything else is `400 INVALID_BODY`. No overlap rule is invented: `unique (tenant_id, person_id, effective_from)` is the only key this path can collide with, and both commands answer `409 COMPENSATION_PERIOD_EXISTS`. As on `person` there is no `RETURNING` — the id comes from `randomUUID()` and the answer is read back through the same select the list uses, so a `404 COMPENSATION_NOT_FOUND` is the one answer for a row this caller cannot reach — although, unlike `person`, a `RETURNING` insert here is not refused by policy, a difference `tests/people-compensation-write.test.ts` pins rather than leaving the earlier reasoning standing. `compensation.created` / `compensation.updated` are appended in the same transaction with the pay row's own id and metadata that is exactly `{ fields: [...] }` — names, never an amount, currency, date or frequency and no before value — so a revoked audit grant rolls the write back, and a `400`, `403`, `404`, `409` or no-op writes nothing. Every response is `Cache-Control: no-store`, the read route, the directory contract and the CSV export are untouched, and the runtime table-grant allowlist is still twelve rows. ADR [0012](docs/adr/0012-compensation-write.md) records the permission, the two policies, the column grant, the read-back and the rejected alternatives.

`GET /v1/work/projects`, `GET /v1/money/invoices` and `GET /v1/content/items` are the three module read surfaces, and each sits behind `{ module: 'work' | 'money' | 'content', operation: 'read' }` with the entitlement checked before the role. The catalog moved the three modules from `planned` to `preview` on 27 October 2026, which is what lets a normal tenant hold them on a contract entitlement; there is no administrative path for catalog status. The routes state no scope predicate — the restrictive policies `module_work_read`, `module_money_read` and `module_content_read`, already installed by `app.apply_module_policies()`, narrow the rows — and they never filter on `tenant_id`. Each takes a literal, case-insensitive `q` through `strpos(lower(...), lower(...))`, counts over the same predicate, orders by `lower(<name>), <id>` with limit and offset, answers `{ items, total, page, pageSize }`, refuses a malformed `page` or `pageSize` with `400 INVALID_QUERY`, sends `Cache-Control: no-store` and writes no audit row on success. Work and Money join `client` for the client name; `content_item` has no client column, so the Content route joins nothing. `runtime-grants.sql` gains exactly three column-only `SELECT` grants in that batch — eleven columns on `invoice`, nine on `content_item` and five on `client` — with no table-level privilege on any of the three and no `INSERT`, `UPDATE` or `DELETE` on `invoice` or `content_item`; the CRM batch later widened `client` to the twenty-five privileges its section records, and these three routes still read only those five columns. `public.project` deliberately keeps its M0 table-level grant because two `tests/module-rls.test.ts` proofs depend on it, and there is still no product write route and no write screen in any of the three modules, so the Work route names only the columns it returns and never selects `source_system`, `source_id`, `import_batch_id`, `imported_at`, `budget_hours`, `manager_user_id` or `tenant_id`; narrowing that grant is deferred to the Work write slice. `public.client` is platform-owned shared directory data with only the permissive `tenant_isolation` policy and no module policy, exactly like `legal_entity` and `org_unit`; every route that reads a client name is module-gated. Money is displayed as stored — `bigint` minor units selected as `::text`, parsed with `Number.parseInt` and refused as a sanitized `500 INTERNAL_ERROR` once the value leaves `Number.isSafeInteger` rather than rounded. ADR [0013](docs/adr/0013-work-money-content-read.md) records the catalog move, the withdrawal of `work.write`, the three grants, the route shape and the landing rule.

`GET /v1/crm/accounts`, `POST /v1/crm/accounts`, `PATCH /v1/crm/accounts/:id`, `GET` and `POST /v1/crm/accounts/:accountId/contacts` and `PATCH /v1/crm/accounts/:accountId/contacts/:contactId` are the CRM account and contact surfaces, and the two reads sit behind `{ module: 'crm', operation: 'read' }` with the four writes behind `{ module: 'crm', operation: 'write' }`, the entitlement checked before the role in both cases. **CRM owns no table**: an account is a shared `client` row and a contact is a shared `client_contact` row, both from `0003_work.sql`, and both carry only the permissive `tenant_isolation` policy and deliberately no CRM module policy, because a module policy on a shared table would narrow the standalone Work and Money reads of the same client row. The three modules therefore name **one** client record rather than three, and a project or an invoice still points at the row a CRM account created. The write bodies are closed, the ids are the server's, the four writes need session, exact `Origin` and the timing-safe CSRF token, the answers carry exactly the eight account keys and the six contact keys, a missing or foreign parent is one `404 ACCOUNT_NOT_FOUND`, a contact that is not on the visible account is one `404 CONTACT_NOT_FOUND`, a taken code is a typed `409 ACCOUNT_CODE_TAKEN` and a second primary a typed `409 CONTACT_PRIMARY_TAKEN` — the demotion of the account's other primaries happens in the same transaction as the promotion. Every write appends `crm.account.created`, `crm.account.updated`, `crm.contact.created` or `crm.contact.updated` with the field names and no values. ADR [0014](docs/adr/0014-crm-accounts-contacts.md) records the catalog move, the two permissions, the forty-five column grants, the route shapes and the shared-record decision.

`apps/web` is a React 19 + Vite single-page app. It has `/login`, `/app`, `/app/people`, `/app/crm`, `/app/work`, `/app/money` and `/app/content`, a small History API router with no redirect parameter, and no routing library. In development and preview, Vite serves it on port 3000 and proxies `/v1` and `/health` to the API on 127.0.0.1:3001; production is expected to serve the bundle and API from one origin behind an edge or reverse proxy, with SPA fallback for application paths. The browser holds only the HttpOnly session cookie; the CSRF token lives in module memory for sign-out, and the theme is the only persistent preference. Navigation is built from the server's effective modules: a module that has a screen is a link — People, CRM, Work, Money and Content — and an effective module without one keeps a **Soon** entry that is not clickable. The landing path is the first navigation module, in catalog order, that has a screen, so a member whose only module is Work lands on `/app/work` and not on `/app`. The three read-only module screens live in `apps/web/src/components/ModuleScreens.tsx` and share one table-shaped list: a heading, a table, an `aria-live` result count, a search form, Previous/Next paging and loading, retryable-error and empty states whose copy never claims the workspace holds no records — the Money empty copy does not say that no invoices were issued, the Work empty copy does not say that there are no projects, and the Content empty copy does not say that there is no content. The Money screen shows the stored figures with the stored ISO currency code beside them, labels the tax column **Tax** — a stored amount, never a rate and never a jurisdiction-derived rule — and computes nothing: no totals across rows, no currency conversion and no overdue calculation. The stored status is shown as stored. There is no write control in any of the three read-only screens. The CRM accounts screen and its contacts panel live in `apps/web/src/components/CrmScreens.tsx`, read and write the shared client records behind the module gate, and offer those write controls only when the context reports `crm.write`. `/app/people` is the directory screen: it keeps the `People` heading and the read/write badge derived from `canWrite`, and adds the fetch of `GET /v1/people`, renders the accessible `People directory` table of Name, Employee code, Work email, Phone and Placement, an `aria-live` result count, a search form that resets to page 1, Previous/Next paging and loading, retryable error and empty states, with copy that never claims the workspace holds nobody and one line stating that the view is limited to the member's role and scope. When the context reports `canWrite`, the toolbar gains an **Add person** control and each row an **Edit** action that opens an inline panel — not a modal — with the six identity fields, `maxLength` taken from the same contract constants, Save and Cancel disabled while a request is in flight, edit pre-filled from the row, and a polite live region announcing `Person created.` or `Person updated.` after a successful save reloads the current query and page. The same row also gains a **Place** action that opens its own panel: it fetches `GET /v1/people/placement-options`, renders one `select` with the server's org units grouped under their legal entities and `Unplaced` only when `canUnplace` is true, pre-selects the stored pair only when it is in the offered list, keeps **Save placement** disabled until the choices both loaded and the selection differs from what is stored, and announces `Placement updated.` on success; the panel states that placement is a directory attribute, not an employment record and that the dates and status live on the row's **Employment** action, and when nothing is placeable it says so and adds that legal entities and org units are created outside this screen today. Each typed API failure (`PERSON_CODE_TAKEN`, `PERSON_EMAIL_TAKEN`, `PLACEMENT_NOT_FOUND`, `PERSON_NOT_FOUND`, `EMPLOYMENT_NOT_FOUND`, `EMPLOYMENT_ENTITY_REQUIRED`, `EMPLOYMENT_STATUS_TRANSITION_INVALID`, `SCOPE_DENIED`, `INVALID_BODY`, `CSRF_INVALID`, network) has its own copy, so no raw server message reaches the page, and a `401` is still handled globally by returning to sign-in. Writes go through the same `request` helper with a JSON body and the in-memory CSRF token in `x-csrf-token`. Every row also carries an **Employment** action regardless of `canWrite`, because opening a history is a read: the panel fetches `GET /v1/people/:id/employments`, then shows a loading state, a retryable error with **Try again**, the empty copy or a table of the ten-key rows (entity name, type, `start – end`, probation end, notice days, status badge), and offers **Add employment** plus a per-row **Edit** only when the context reports `canWrite` — so a `people.read`-only member sees the dates and no control at all, which the second browser journey asserts. Create is five fields with no status, update is six, Save is disabled while a request is in flight, while a create has no start date or while an update names nothing that differs, and a success closes the form, announces `Employment added.` / `Employment updated.` in the same polite live region and refetches the history. A row additionally carries a **Compensation** action only when `/v1/context` reports `people.compensation.read` — for every other reader the action is absent from the row, not disabled — and that panel fetches `GET /v1/people/:id/compensations`, shows loading, a retryable error with **Try again** in a polite live region, the empty copy or a table of `effective_from`, `effective_to` (an em dash while open), the amount `formatCompensationAmount` renders from the stored minor units with the stored ISO code inside that same cell, and the stored frequency label. What the write permission decides is the shape of that table and the controls beside it: with `people.compensation.write` in the context the table gains a fifth **Actions** column with an **Edit compensation from <date>** per row and the toolbar gains **Add compensation**, whose five-field form keeps **Save compensation** disabled until the opening date, amount and currency are filled — and, on the edit path, until the patch differs from what is stored, because the form opens prefilled — closes on `Compensation added.` / `Compensation updated.` in the same polite live region and refetches the history, and carries the create note that a new record opens on its own date and the update note that this amends the stored row in place; without it the panel is exactly what 0011 shipped — four columns, no field, one **Close** — and the fine print branches on the same permission the controls do, so a reader who is not a writer is told the panel is read-only *for them* and that a member whose role also holds the pay write can add and amend inside their own scope, while both branches say no record can be deleted by anyone and that a row is not a monthly or annual salary worked out from it. There is no delete, restore or person-status control, no legal entity or org unit editor, no org-tree view, no import, no export button, no bulk edit and no fake rows. It shows no scope label, because the runtime cannot read `membership_scope`. Rows arrive already narrowed by the database; the client filters nothing. A member without readable People sees an access state instead. Every value is rendered as a React text node, nothing is written to browser storage beyond the theme, and the document has no horizontal overflow at 390, 768 or 1440 px — the table wrapper scrolls instead and the form grid folds to one column. Client rendering is not an authorization boundary. Eight Playwright/Chromium journeys run against the built output, a disposable PostgreSQL database and an in-process API — three in `tests/e2e/people.spec.ts` (the owner's directory, write, place, employment, compensation-read and un-place cycle; a `people.read`-only member who opens a history, is offered no write control and finds no **Compensation** action on any row; and the compensation read without the write), two in `tests/e2e/modules.spec.ts` (the owner's Work, Money and Content screens and a member without `money.read` who sees no Money navigation entry and no invoice figure anywhere on the page), and three in `tests/e2e/crm.spec.ts` (the CRM-only owner who creates an account, edits it and manages two contacts; a `crm.read`-only member who sees the accounts and the contacts and no write control; and an hr member inside the same CRM-entitled tenant who gets no CRM navigation entry, no CRM data and no CRM request) — and they are declared in CI but the workflow has never run.

Proof routes are disabled by default and enabled only by tests. There is no People delete, restore or person-status screen, no payroll or payslip screen, no bulk edit, no import, no export button, no invitation or password-reset UI, and no write control in the Work, Money or Content screens. The CRM screen writes accounts and contacts on the shared client records; there is no CRM lead, pipeline, activity, forecast, export or delete surface, and a contact cannot be removed because the shared `client_contact` row has no soft-delete column. The write paths cover core identity, placement and employment history: there is no per-person detail route, no route that writes `person.status`, `user_id`, `personal_email`, `date_of_birth` or `gender`, no route that names `work_jurisdiction_id`, `source_system`, `source_id` or `import_batch_id` on `employment` or any compensation or statutory column anywhere, no route that deletes or archives an employment row, no cross-person or paged employment list, no route that creates, renames or retires a legal entity or org unit, and no delete or restore counterpart to create. The export has no filters, column selection, date range, Client or Work variant, asynchronous/background mode, signed URL, storage, export history, dedicated export permission or rate limit; full-suite export and re-import are not built. Scope values are not exposed in `/v1/context`, in any UI label or through any read API — the database narrows rows and the client only sees the result — and project and client scope, employee self-scope as a usable permission, scope or role administration in the application, seat enforcement, password reset, MFA, OAuth, email delivery, tenant switching, device list, session rotation and distributed rate limiting are not implemented. Authenticated access denials on gated routes are audited as `authorization.denied`; unauthenticated requests and non-access failures are not. Do not treat this skeleton as a production authentication layer or the directory export as a complete portability feature.

Provisioning and entitlement changes are owner-only libraries used by the `db:provision` CLI; invitations are created by the owner-only `db:invite` CLI; the person/user link and a membership's scope rows are written by the owner-only `db:scope` CLI (`packages/db/src/scope.ts`), which audits each change in its transaction. None is routed through the API, and none takes a runtime or auth connection.
