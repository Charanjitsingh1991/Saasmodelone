# SaaSModels One

Modular SaaS suite for service businesses. This repository is the product; the marketing site is not part of it.

Current milestone: **M0 has not exited**; M1 has started with the People scope database layer in `suite/db/migrations/0012_people_scope.sql`, its owner-only authoring path in `packages/db/src/scope.ts` behind `pnpm db:scope` ([ADR 0007](suite/docs/adr/0007-people-scope.md)), and the People directory in `apps/web`: the read path (`GET /v1/people`) plus the core-identity write path (`POST /v1/people`, `PATCH /v1/people/:id`, [ADR 0008](suite/docs/adr/0008-people-write-path.md)), the placement path (`GET /v1/people/placement-options`, `PATCH /v1/people/:id/placement`, [ADR 0009](suite/docs/adr/0009-people-placement.md)), the employment-history path (`GET /v1/people/:id/employments`, `POST /v1/people/:id/employments`, `PATCH /v1/people/:id/employments/:employmentId`, [ADR 0010](suite/docs/adr/0010-people-employment.md)) and the compensation-history read path (`GET /v1/people/:id/compensations`, behind its own `people.compensation.read` permission and `suite/db/migrations/0013_compensation_read.sql`, [ADR 0011](suite/docs/adr/0011-compensation-read.md)) — a read only: no compensation write exists. Payroll calculation, statutory packs, CRM/Work/Money/Content domain screens and Switch import are out of scope until their roadmap milestone. See [AGENTS.md](AGENTS.md) and [suite/docs/roadmap.md](suite/docs/roadmap.md).

## Prerequisites

- Node.js 22.12 or later, below 25
- pnpm 10.18
- PostgreSQL 17 locally. `compose.yaml` is the canonical harness; any local PostgreSQL 17 on port 54329 can be used instead.
- Playwright Chromium, installed with `pnpm exec playwright install chromium`, only for the two browser journeys.

## Local setup

```bash
cp .env.example .env
docker compose up -d
pnpm install
pnpm db:setup
pnpm test
```

`pnpm db:setup` runs three separate privileged steps:

1. `db:bootstrap` creates `saas_owner`, `saas_runtime`, `saas_auth` and `saas_worker`, creates the `saasmodels` database owned by `saas_owner`, and removes PUBLIC creation rights.
2. `db:migrate` applies `suite/db/migrations/*.sql` in order as `saas_owner`, records SHA-256 checksums in `infra.schema_migration`, and reapplies the runtime and auth grant allowlists.
3. `db:seed` applies the idempotent module catalog.

The migration runner refuses to continue when an applied file's checksum changes, when a migration was interrupted, or when it previously failed. Reviewed migrations are never rewritten; add a forward migration instead.

`pnpm drill:restore` runs the backup-and-restore drill against the local developer database when PostgreSQL 17 client binaries are installed (default `D:/tools/pg17/pgsql/bin`, overridable with `PG_BIN_DIR`): a custom-format `pg_dump` into gitignored `var/backups` with its size and SHA-256 recorded, a restore into a throwaway `saasmodels_drill_<timestamp>` database, a parity check of table counts, load-bearing row counts, RLS and policy counts, the runtime grant inventory and a runtime-role query under `app.tenant_id`, then the drop of the drill database. The source database is read-only to the drill and is never a restore target. It proves one logical local restore on synthetic data only — no schedule, encryption, PITR or CI coverage. See [suite/docs/testing.md](suite/docs/testing.md) §2.14.

## Web app

The M0 client is a React 19 + Vite single-page app in `apps/web`. Run the API and the web server in two terminals:

```bash
pnpm dev:api   # Fastify on 127.0.0.1:3001, loading .env
pnpm dev:web   # Vite on http://localhost:3000
```

Vite proxies `/v1` and `/health` from port 3000 to `http://127.0.0.1:3001`; set `VITE_API_PROXY_TARGET` to override the target. Port 3000 is `strictPort`, so a second dev server fails instead of moving to another port. `pnpm build:web` type-checks and writes the static bundle to `apps/web/dist`; `pnpm test:e2e` builds that bundle first, through the Playwright webServer command, then runs the fresh output against a disposable database and an in-process API, so the journeys can never pass against stale or missing `dist`.

Production must serve the static bundle and the API from one origin behind an edge or reverse proxy, forward `/v1` and `/health`, preserve the browser's `Origin` unchanged (the API requires an exact match) and return `index.html` for unknown application paths so `/app` and `/app/people` survive a reload. No production deployment, Content-Security-Policy or production security-header configuration exists or is claimed. See [ADR 0006](suite/docs/adr/0006-web-shell.md).

The browser never stores the session token: `saas_session` is HttpOnly, and the CSRF value used for sign-out is held in module memory only. The theme is the only persisted preference. Client routing and navigation filtering are presentation only; the API repeats the entitlement and role checks on every request and the database applies the scope policies underneath them. `apps/web` imports only `@saasmodels/contracts`, and the client uses no component library, CSS framework, external font, CDN, analytics or runtime third-party script.

## Roles

| URL | Role | Use |
| --- | --- | --- |
| `DB_ADMIN_URL` | PostgreSQL superuser | Local bootstrap only |
| `DB_OWNER_URL` | `saas_owner` | Migrations, seeds, provisioning, invitations |
| `DB_RUNTIME_URL` | `saas_runtime` | Tenant business data through the application |
| `DB_AUTH_URL` | `saas_auth` | Identity lookups and session storage |
| `DB_WORKER_URL` | `saas_worker` | Outbox claiming and disposition through `app.outbox_*` helpers only |

`saas_runtime` is not the table owner, does not have `BYPASSRLS`, cannot create schemas or tables, cannot write the module catalog, and cannot execute administrative procedures. `saas_auth` is a separate login role for identity only: it can read and update the identity columns it needs, manage `auth_session` and `invitation`, and has no access to tenant business data, the module catalog or audit. Its table and function grants are an explicit allowlist in [packages/db/sql/auth-grants.sql](packages/db/sql/auth-grants.sql), reapplied after every migration alongside the runtime allowlist.

`saas_worker` is narrower still: it holds no table or column privilege anywhere, including on `domain_event`, and no DDL. It can execute exactly four outbox helpers plus `app.current_tenant_id`, `app.has_platform_access`, `app.has_module_read` and `app.has_module_write`, which is what the tenant transaction gate needs to run. Those grants live in [suite/db/migrations/0011_outbox.sql](suite/db/migrations/0011_outbox.sql), not in the runtime or auth allowlist files, because the blanket revokes in `runtime-grants.sql` target only `public` and `saas_runtime`; the worker surface is asserted as an exact list in [tests/schema-inventory.test.ts](tests/schema-inventory.test.ts).

The harness refuses any database URL that does not point at localhost, `127.0.0.1`, `[::1]` or a Unix socket. It will not connect to a remote database.

## Outbox worker

[Suite/db/migrations/0011_outbox.sql](suite/db/migrations/0011_outbox.sql) adds the lease mechanics to the `domain_event` table shipped by 0001 (`status`, `lease_owner`, `lease_expires_at`, `next_attempt_at`, a partial `(tenant_id, occurred_at)` claim index) and four `SECURITY DEFINER` helpers in the `app` schema — `outbox_claimed_guard`, `outbox_claim`, `outbox_mark_published`, `outbox_record_failure` — that are searchable-path pinned, filter explicitly on `app.tenant_id` on every read and write, and raise when the GUC is unset or not a valid UUID. `EXECUTE` is granted only to `saas_worker`; the `PUBLIC` grant is revoked.

`apps/worker` exports `runOutboxPass(pool, tenantId, options)` and `startOutboxWorker(pool, options)`. Each pass opens the tenant through `withTenantTransaction` with an entitlement gate (default `people`/`read`), claims up to `batchSize` (20) events under a `leaseSeconds` (60) lease, runs the registered handler for each event's `type` after the claim transaction closes, then marks published on success or records the failure with exponential backoff (`backoffSeconds` 2 doubling to `maxBackoffSeconds` 3600) and moves the event to `dead` once `attempts` reaches `maxAttempts` (5). `attempts` increments at claim only. A tenant that fails the platform or entitlement check is skipped with `platform_denied` or `entitlement_denied` and no handler runs. `startOutboxWorker` polls on `pollIntervalMs` per tenant in a `setTimeout` chain and is stopped with `stop()`.

Delivery is at-least-once, not exactly-once: an expired lease lets a second worker re-claim a row while the first handler still runs, and the late `mark_published` or `record_failure` from the lost lease is refused because the helpers pin the lease timestamp. Handlers must therefore be idempotent, and the suite tests duplicate delivery, mid-run lease expiry, retry backoff, dead-lettering and cross-tenant invisibility against a real disposable database.

No producer is wired. No current M0 write path can emit a domain event inside its own state-change transaction without redefining a reviewed 0010 identity helper or giving `saas_auth` a new cross-tenant write surface, so this task ships consumer machinery only: `domain_event` is empty in a seeded database, no process starts `startOutboxWorker`, no consumer other than test handlers exists, and there is no external broker, cron, webhook or deployment — the queue is Postgres alone. The first producer and a running consumer are M1 work. M0 has not exited.

## Authentication configuration

The API requires `DB_RUNTIME_URL`, `DB_AUTH_URL` and `APP_ORIGIN`. `APP_ORIGIN` is the exact browser origin allowed to send state-changing requests; there is no wildcard and no proxy-header trust. `COOKIE_SECURE` defaults to true when `NODE_ENV=production` and can be overridden for local HTTP. `SAAS_AUTH_PASSWORD` is required by `db:bootstrap`; `TEST_DB_AUTH_URL` supplies the same role to the test harness. `SAAS_WORKER_PASSWORD` is required by `db:bootstrap` for the same reason, and `DB_WORKER_URL` / `TEST_DB_WORKER_URL` supply that role to the worker and to the test harness.

Email/password login uses Argon2id, and the browser holds only an opaque `saas_session` cookie whose SHA-256 hash is stored server-side. Identity is global (`app_user.email` is unique) while memberships are per tenant, so one user can sign in to several tenants with the same password. Invitations are created by the owner-only `pnpm db:invite` command and accepted once through the API; a first-time invitee sets a password, and an active user invited to a second tenant verifies its existing one. Login is rate-limited per source address and per email in memory, and auth responses are sent `Cache-Control: no-store`. The web shell has email/password sign-in and sign-out, a generic `401` message that does not identify the failing field, a distinct `429` message, and a retryable network state; credentials are not placed in the URL, logs, local storage or session storage. There is no password-reset, invitation-acceptance, MFA, OAuth, tenant-switching or session-management UI yet, and no email delivery, session rotation, device list or distributed rate limiting. These are target behaviours, not shipping features.

## Authorization

Role authorization is server-side and shared. `@saasmodels/contracts` defines the seven membership roles, the five published permissions (`people.read`, `people.write`, `people.compensation.read`, `work.read`, `work.write`, in that order) and the role matrix. `withMemberTransaction` checks membership, platform access, the module entitlement and then the role permission, in that order, so an unentitled module never discloses role policy; since T22 the gate can also name a permission of its own instead of the one derived from its module and operation, and a role denial then names the permission actually asked. Owner and admin hold all five permissions; HR holds People read, People write and the compensation read; finance holds People read, the compensation read and Work read; manager holds People read and Work read/write; auditor holds People read and Work read; employee holds none, unchanged by 0012 and unchanged by the fifth permission, so an employee request still denies at `ROLE_DENIED` before any scope policy is reached. `people.compensation.read` is the first permission another one does not imply: `people.read` lists the directory and opens an employment history, and reading what a colleague costs needs the extra grant. `/v1/context` returns canonical permissions and only the modules effective under both entitlement and role, each with the catalog `name` and `sortOrder`, ordered by `sort_order, code`, and the response is `Cache-Control: no-store`. Authenticated access denials are appended as `authorization.denied` with reason, method, registered route template and, where known, module/operation/permission; raw URLs, tokens, cookies and headers are not recorded. The audit is best-effort, so a failed audit write is logged and the denial is still returned.

Scope is the third layer and, as of M1's first slice, it is a database property rather than request code. [suite/db/migrations/0012_people_scope.sql](suite/db/migrations/0012_people_scope.sql) adds `person.user_id`, the `membership_scope` table and eight `AS RESTRICTIVE` policies on `person` and `employment` that call owner-owned `SECURITY DEFINER` helpers; [suite/db/migrations/0013_compensation_read.sql](suite/db/migrations/0013_compensation_read.sql) adds the ninth, `scope_read` on `compensation`, using the same read oracle, so a salary history is narrowed by the decision that already narrows the directory. A member with no scope row sees the whole tenant; a scoped member sees their legal entity, or their org unit and its descendants; a linked employee sees exactly their own person row and can write nothing; an unplaced person is visible only to a tenant-wide member. Because the policies only narrow and a transaction that sets `app.tenant_id` without `app.user_id` is deliberately not narrowed at all, the system path keeps its M0 visibility — the residual is pinned by `tests/scope.test.ts` and recorded as threat T36. See [ADR 0007](suite/docs/adr/0007-people-scope.md).

Scope is written out of band, not by the product. `packages/db/src/scope.ts` behind `pnpm db:scope` links and unlinks a person to a user and replaces one membership's scope rows, connecting with `DB_OWNER_URL`, requiring the actor to hold an active `owner` membership in that tenant, re-checking every id with tenant-scoped queries rather than trusting caller input, refusing duplicates, unknown or cross-tenant targets, `--tenant-wide` combined with scopes, and any `employee` membership, and appending its audit row in the same transaction so an audit failure rolls the change back. It is reachable from no route, and the runtime and worker roles gain no privilege on `membership_scope` or `person.user_id`. That owner-only path is what threat T37 records, with the residual that a valid-but-wrong grant by an authorized operator is detectable only by reading those audit rows on the owner connection. Since 0012 the policies are exercised from the request layer: `GET /v1/people` and `GET /v1/people/export` both run inside a member transaction that sets `app.user_id`, so a scoped manager's directory page and export are narrowed by the database itself. What is still not built: scope values in `/v1/context` or any scope label in the UI, project and client scope, a scope read or administration API, and role administration with seat enforcement.

The web shell has three routes: `/login`, `/app` and `/app/people`. After sign-in it loads the session and then the context, shows the role, a theme toggle, sign-out and a module navigation built only from the effective modules the server returned. People is the only module with a screen; other effective modules are labelled as not yet shipped and are not clickable. `/app/people` renders the directory read path: a search form, an `aria-live` result count, a table of the people the member can see (Name, Employee code, Work email, Phone, Placement) and Previous/Next paging, with loading, retryable error and empty states. Its empty copy says no people are visible in this view, never that the workspace holds nobody, and one line states that the view is limited by the member's role and scope. It shows an **Add person** control and per-row **Edit** and **Place** actions only for a member whose role holds `people.write`, and a member without that permission gets the same table with no write affordance at all — but every reader still gets the per-row **Employment** action, because opening a history is a read, while the per-row **Compensation** action appears only for a role the context reports as holding `people.compensation.read` and is absent — not disabled — for every other reader. The Placement cell shows the legal entity and org unit names the server joined in, or an em dash when the person is unplaced or a referenced row has been retired. There is no person delete, restore or status control, no legal entity or org unit editor, no invitation UI and no export button. A member without readable People who opens `/app/people` sees an access state listing the modules they do have, never the directory shell. The screen renders only React text nodes — no `dangerouslySetInnerHTML`, nothing written to browser storage beyond the theme — and it does not label any row with a scope, because the runtime cannot read `membership_scope`. Client routing is not an authorization boundary; the API repeats every check and the database narrows the rows.

## People directory read path

`GET /v1/people` is the first member data route narrowed by the 0012 scope policies. It requires a valid session and runs its queries inside `withMemberTransaction` with `{ module: 'people', operation: 'read' }`, so entitlement, then role, then the restrictive scope policies apply in that order, and a denial produces the existing typed codes plus an `authorization.denied` audit row. Because the transaction sets both `app.tenant_id` and `app.user_id`, no scope predicate is re-implemented in SQL or TypeScript — the same policies that narrow the export narrow this route.

The response is exactly `PeopleListResponse` from `@saasmodels/contracts`: `items` (each with `id`, `employeeCode`, `firstName`, `lastName`, `displayName`, `workEmail`, `phone`, `legalEntityId`, `legalEntityName`, `orgUnitId`, `orgUnitName`), `total` as a JSON number, and the effective `page` and `pageSize`. It selects the seven directory columns the runtime role is granted on `person`, the two placement ids from the same row, and the two names through a left join to `legal_entity` and `org_unit` that each guard on `deleted_at is null`, so a retired reference row never keeps a name beside an id that is still stored; a null name never means a null id. It filters `deleted_at is null`, and never reads `tenant_id`, `user_id`, `personal_email`, `date_of_birth` or `gender`. `q` is a trimmed, literal, case-insensitive substring over `display_name`, `employee_code` and `work_email` through `strpos(lower(...), lower($n))`, so `%` and `_` are data rather than wildcards; `page` defaults to 1 and `pageSize` to 20, capped at 50. A repeated, non-integer, out-of-range or over-length parameter is rejected with `400 INVALID_QUERY` before any query runs, and a page past the end returns an empty `items` array with the true `total` rather than an error. Ordering is `lower(display_name), id`, so paging is deterministic. Every `/v1/people` response, including denials and `400`s, is `Cache-Control: no-store`. A successful read writes no audit row; the read path is a plain `SELECT`.

## People directory write path

`POST /v1/people` and `PATCH /v1/people/:id` are the first member writes in the suite. Both require a valid session, then a matching `x-csrf-token` header — the same timing-safe check the logout route uses, now factored into one helper — and a missing or wrong token returns `403 CSRF_INVALID` before any database work. The global origin hook still refuses a cross-site `POST` or `PATCH` with `403 ORIGIN_DENIED` first, so a forged form never reaches either check. Both routes then run in `withMemberTransaction` with `{ module: 'people', operation: 'write' }`, so the order stays entitlement, then role, then the restrictive 0012 policies, and the body is parsed only after that gate: a `people.read` role sending a malformed body is still a `ROLE_DENIED`, not a `400`.

Only the six core identity fields are writable here — `firstName`, `lastName`, `displayName`, `employeeCode`, `workEmail`, `phone` — each with the contract's length limit. The body must be a plain JSON object; an array, a non-object, an empty object, a client-supplied `id`, or any unknown key such as `status`, `legalEntityId`, `orgUnitId`, `userId`, `personalEmail` or `dateOfBirth` is a `400 INVALID_BODY` with no echo of the submitted values. Placement is not one of these routes' concerns: it is the pair below, on its own route. On create, a missing or blank display name is derived from the names; on update, an absent key means unchanged, a null or blank optional means cleared, and a null display name re-derives. `work_email` is `citext`, so uniqueness and change detection are case-insensitive. A unique violation maps to a typed code without repeating the value: `PERSON_CODE_TAKEN`, `PERSON_EMAIL_TAKEN`, or `PERSON_CONFLICT` for anything else.

Creates go through `app.person_placement_in_scope(null, null)` first: a new person starts unplaced, which only a tenant-wide member may record, so a scoped member gets `403 SCOPE_DENIED` and no insert. That is deliberate — the write-side policy refuses an out-of-scope placement, and the route says so instead of letting the database raise a `42501`. Updates, exports and reads are narrowed by the same policies: the target row is read inside the transaction, and a row that is unknown, malformed, soft-deleted, in another tenant or outside the member's scope returns the same `404 PERSON_NOT_FOUND`, so no response distinguishes "does not exist" from "not yours to see". An update that changes nothing returns the stored item with no `UPDATE` and no audit row; last write wins, with no version column and no optimistic lock.

The API generates the new row's UUID with `randomUUID()` and inserts it explicitly, with no `RETURNING`, then reads the directory row back in the same transaction. `INSERT ... RETURNING` is refused by the restrictive `scope_read` policy, because `person_visible(id)` re-queries `person` with a snapshot that cannot observe a row created by the same command; [ADR 0008](suite/docs/adr/0008-people-write-path.md) records the reproduction and why the explicit-id insert plus same-transaction `SELECT` avoids `RETURNING` without weakening a policy. If that read-back finds nothing, the route fails closed with the sanitized `500 INTERNAL_ERROR` — it is an internal invariant, not a client error. To support it, `saas_runtime` holds 10 `SELECT`, 8 `INSERT` and 8 `UPDATE` column privileges on `person` (26 in total): `id` and `tenant_id` are insertable so a create can name and own its row, `id` is deliberately not updatable, and there is still no table-level DML, no `DELETE`, and no grant on `status`, `user_id`, `deleted_at`, the timestamps or the personal and demographic columns. The two placement columns are selectable and updatable but **not** insertable, which is what makes every new person unplaced. RLS stays the tenant and scope boundary for every write.

`person.created` and `person.updated` audit rows are appended in the same transaction as the write, so a failed audit rolls the write back and returns a sanitized `500 INTERNAL_ERROR`. Metadata carries field names only — `fields` on create, `changedFields` on update — never before or after values, so a phone number or work email is not duplicated into the audit trail. Scope denials and object misses write no audit row, which ADR 0008 explains: the scope verdict comes from RLS with no actor-level event to record, and a `404` writes nothing so a probe cannot use the audit table to map the tenant. Every `/v1/people` response is `Cache-Control: no-store`, matched by path prefix so writes, denials and `400`s are covered.

The People screen shows an **Add person** control and per-row **Edit** and **Place** actions only when `people.canWrite` is true, with an inline two-column panel rather than a modal, `maxLength` from the same contract constants, and a polite live region that announces `Person created.`, `Person updated.` or `Placement updated.` after a successful save and reload of the current query and page. Each typed failure has its own honest copy, so raw server messages never reach the page, and a `401` still hands the app back to the global sign-in handler. There is no person delete, restore or status change, no legal entity or org unit editor, no import, no CSV change, no bulk edit and no scope label.

## People placement

`PATCH /v1/people/:id/placement` moves a person onto a legal entity, onto an org unit inside one, or back to unplaced. It is a directory attribute, not an employment record: `status`, the employment and compensation columns, `location_id`, `manager_person_id`, `designation` and the two date columns are untouched, and no employment row is created or changed. It writes `legal_entity_id` and `org_unit_id` onto a row that already exists — the person `INSERT` grant list has no placement column, so a create can never place anybody — and [ADR 0009](suite/docs/adr/0009-people-placement.md) records why placement is its own route with its own contract rather than two more keys on the identity patch.

The body is always the whole statement: exactly `legalEntityId` and `orgUnitId`, each a UUID or `null`. There is no omit-it-to-keep-it — an absent or extra key, an empty object, an array, a non-string or malformed UUID is one `400 INVALID_BODY` with nothing echoed — and an org unit with a null entity is refused the same way, because a unit always sits inside an entity. Session, exact `Origin` and a matching `x-csrf-token` come before any database work, and the route runs in `withMemberTransaction` under `{ module: 'people', operation: 'write' }`, so entitlement, then role, then the 0012 policies are settled before the body is parsed.

Every scope answer comes from `app.person_placement_in_scope(legal_entity_id, org_unit_id)` — the same security-definer helper the write policies call — and no scope rule is restated in SQL or TypeScript. `GET /v1/people/placement-options` asks it four times: `canUnplace` is the both-null call, an entity's `placeable` flag is the entity-only call, and a unit is offered only when its own `(entity, unit)` pair is approved. An entity is listed either because the member may place on it alone or because it owns a unit they may place into, which is why the response carries `placeable` and the screen renders a non-placeable entity as a group heading only. The options route is a `GET` behind the same **write** gate: a member who cannot place anybody has no reason to read the org structure.

Unreachable targets are hidden, not explained. An unknown, retired, cross-tenant, out-of-scope or wrong-entity legal entity or org unit answers `404 PLACEMENT_NOT_FOUND`, and an unknown, malformed, soft-deleted, cross-tenant or out-of-scope person answers `404 PERSON_NOT_FOUND`, so a scoped member cannot use these calls to find out whether an org unit exists. The one case with no id to hide — the both-null unplace, which only a tenant-wide member may do — answers `403 SCOPE_DENIED` instead. A unit named under a different real entity is refused by the route rather than by a constraint, because `person` carries composite foreign keys to each table but nothing ties the unit's entity to the entity on the row.

The response is the same eleven-key directory item the list returns, read back through one shared select after the write; `UPDATE ... RETURNING` cannot carry a joined column, so both write paths now read the row back in the same transaction and a `rowCount` other than one is a sanitized `500` that rolls the write and its audit back. A placement that changes nothing issues no `UPDATE` and writes no audit row. A change appends `person.placement.changed` in the same transaction with `{ module, legalEntityId, orgUnitId, previousLegalEntityId, previousOrgUnitId }` — ids only, no names, emails or field values — and the previous pair is recorded because a placement is the one directory change that alters which colleagues can see the row. `Scope` and `404` refusals write no audit row, and every response on both routes is `Cache-Control: no-store`.

To read the names, `saas_runtime` now holds column-only `SELECT` on exactly `legal_entity (id, name, code, deleted_at)` and `org_unit (id, name, legal_entity_id, deleted_at)` — eight column privileges, no table-level privilege, no write path of any kind and no grant on either table's `tenant_id`. Cross-tenant references are unreachable twice over: the join addresses a row by its globally unique id and never filters on `tenant_id`, the reference table's `tenant_isolation` policy hides any other tenant's row from the lookup, and the composite `(tenant_id, id)` foreign key from `person` makes the value un-storable. Legal entity and org unit administration does not exist, so these two tables remain read-only to the application.

The row's **Place** action opens its own panel: the choices come from the server, `Unplaced` is offered only when `canUnplace` says so, the stored placement is pre-selected only when it is in the offered list, and **Save placement** stays disabled until the selection both arrived and differs from what is stored — so the screen can never submit a change it never displayed. When nothing is placeable the copy says no legal entity or org unit is available yet and that they are created outside this screen today. Placement is absent from the CSV export, which still emits the same seven identity columns; that divergence is recorded in ADR 0009 rather than quietly closed.

Not built: project and client scope, scope labels or a scope read API, any `/v1/context` change — the context response still reports entitlements and permissions only, so a client cannot tell a tenant-wide member from a scoped one. Legal entity and org unit administration, the org-tree view, bulk placement, placement in the export, placement history read and an approval or undo on a move do not exist.

## People employment history

`GET /v1/people/:id/employments`, `POST /v1/people/:id/employments` and `PATCH /v1/people/:id/employments/:employmentId` are the first product routes to write the `employment` table, and the first place where a read and a write on one table are deliberately decided by two different helpers. The `GET` runs under the People **read** gate and holds no scope statement of its own: `employment`'s restrictive `scope_read` policy calls `app.person_visible(person_id)`, the read oracle that also narrows the directory and that carries the linked-employee self exception, so anyone who may see a colleague may open that colleague's whole history. Each write runs under the People **write** gate and, inside the same member transaction, selects `app.person_in_scope(person_id)` before touching a row. That is not the policy restated: `saas_runtime` holds whole-table `INSERT`, `UPDATE` and `DELETE` on `employment` from the M0 tenant-isolation proof surface, so without the pre-check a refused create raised `42501` and a refused update matched zero rows, and in both cases the caller received a sanitized `500` for what is a scope decision. Asking the write oracle first answers a typed `403 SCOPE_DENIED`, and because the two oracles differ in exactly one respect — an employee is always false for write, and a person linked to the caller gets no exception there — the same membership can be told "you may read this" and "you may not maintain this" at the same time. [ADR 0010](suite/docs/adr/0010-people-employment.md) records that split and the alternatives rejected.

The write surface is closed and partly derived. A create accepts `employmentType` and `startDate` plus the optional `endDate`, `probationEndDate` and `noticeDays`; a patch may additionally name `status`, an absent key means unchanged and an explicit `null` clears only those three optionals. There is no `personId` in the body because the path supplies it, and no `legalEntityId`: the entity is copied from `person.legal_entity_id` at the moment of the write, so an unplaced person or one placed on a retired entity answers `409 EMPLOYMENT_ENTITY_REQUIRED` and a row keeps the entity it was created against even after the person is moved elsewhere. `status` is absent from the insert column list, so a new row is `active` because the column default says so and not because a caller said so, and `work_jurisdiction_id`, `source_system`, `source_id`, `import_batch_id` and the timestamps are named by no statement. A date must be shaped `YYYY-MM-DD` *and* be a real day, an end or probation date cannot precede the start, `ended` requires an end date, `notice_days` is a whole number from 0 to `EMPLOYMENT_NOTICE_DAYS_MAX`, and a status moves only forward — `active` to `ended` or `cancelled`, never back, and naming the status a row already has is a no-op that writes neither row nor event.

Unreachable targets stay hidden. An unknown, malformed, soft-deleted, cross-tenant or out-of-scope person id — and an entity id, or the person's own employment id, used where a person id belongs — is the one `404 PERSON_NOT_FOUND` the identity and placement routes already give, and an employment id that is not a row of that person is `404 EMPLOYMENT_NOT_FOUND`. Both writes require the session, an exact `Origin` and the timing-safe CSRF token; the history `GET` requires none of them. A successful write appends `employment.created` or `employment.updated` in the same transaction, with the employment row's own id as entity ID and sorted field names only in metadata — no date, no notice period, no status — so a revoked audit grant rolls the write back to a sanitized `500`; a refusal, a no-op patch and a read write nothing. Every response on all three routes is `Cache-Control: no-store`, and the slice adds no migration, no policy, no helper and no grant change.

On the screen every directory row carries an **Employment** action regardless of `canWrite`, because opening a history is a read; the panel shows loading, retryable error, empty or the ten-key table, and **Add employment** and the per-row **Edit** appear only when the context reports `canWrite`. The list is unpaginated and unbounded — every row for one person, newest first — which is a recorded limit rather than a design. Not built: any compensation write, payroll, jurisdiction or statutory rules, an employment delete, archive or restore, a cross-person or paged employment list, effective-dated reconciliation between a person's placement and their employment's entity, a "current employment" derivation and any employee-facing read, because `employee` still holds no permission and is refused before any policy runs.

## People compensation history

`GET /v1/people/:id/compensations` is the first route anywhere in the suite behind a permission the module's own read does not imply, and the first to disclose money. It requires a valid session and runs inside `withMemberTransaction` with `{ module: 'people', operation: 'read', permission: 'people.compensation.read' }`: the optional `permission` on the gate replaces only the role question the gate asks, so entitlement is still checked first against the `people` module and the `read` operation — an unentitled tenant answers `MODULE_NOT_ENTITLED` here exactly as it does on every other People path — and `MODULE_OPERATIONS` stays `read`/`write` because salary is not a third operation. A role denial answers `403 ROLE_DENIED` naming `people.compensation.read` and the person id is never looked at, so a `manager`, an `auditor` or an `employee` cannot use the route to test whether a colleague has a salary row. [ADR 0011](suite/docs/adr/0011-compensation-read.md) records that shape and the alternatives rejected.

Rows are narrowed by the database, not by the route. `suite/db/migrations/0013_compensation_read.sql` adds one `AS RESTRICTIVE` policy — `create policy scope_read on public.compensation as restrictive for select using (app.person_visible(person_id))` — the ninth scope policy and the first on a third table, and it landed in the same slice as the grant because `tests/scope.test.ts` derives, from the catalog, the set of runtime-readable `person_id` tables and requires that read policy on each. `packages/db/sql/runtime-grants.sql` gives `saas_runtime` column-only `SELECT` on exactly seven columns — `id`, `person_id`, `effective_from`, `effective_to`, `ctc_minor`, `currency`, `pay_frequency` — with `has_table_privilege` false for all four commands and no table-level entry, so `structure`, the source and import columns and the timestamps are outside the role's reach by grant rather than by convention. The route itself states no scope predicate: after the gate it guards the id shape, runs the directory select as the visibility test and answers one `404 PERSON_NOT_FOUND` for an unknown, malformed, soft-deleted, cross-tenant or out-of-scope person, so the route cannot probe for people a member may not list. The list is every row for that one person ordered `effective_from desc` as `{ items, total }`, unpaginated, `Cache-Control: no-store`, no CSRF token (it is a `GET`), and no audit row on success.

A figure that cannot be a JavaScript integer is refused rather than rounded: `ctc_minor` is selected with `::text`, parsed, and rejected as a sanitized `500 INTERNAL_ERROR` once it falls outside `Number.isSafeInteger`, so no salary silently becomes `…992`. Nothing is annualised, prorated or labelled — the seven keys are the stored values, and `formatCompensationAmount` in `apps/web` renders the stored minor units over 100 with the stored ISO code beside them, which assumes two fractional digits and is recorded as a limit. On screen a directory row carries a **Compensation** action only when `/v1/context` reports `people.compensation.read`; for every other reader the action is absent, not disabled. The panel is read-only in fact — one **Close** control, no input, select, textarea or save button anywhere in it — with loading, an empty-history copy, a retryable error in a polite live region with **Try again**, a four-column table (`Effective from`, `Effective to`, `Amount`, `Pay frequency` — the amount cell carrying the stored ISO code, an em dash where `effective_to` is null) and fine print that states the build cannot add, change or remove a salary record and that a row is a stored amount with its frequency, not a monthly or annual salary worked out from it. No compensation write exists: `people.compensation.write` is not a published permission, no route accepts one, the runtime holds no DML on the table and no write policy exists to test. There is no salary overview, aggregate, export column, cross-person list, paging or read audit — who looked at whose pay is not recorded anywhere.

## People directory export

`GET /v1/people/export` is the first production module route and is registered whether or not proof routes are enabled. It requires a valid session and is gated by `withMemberTransaction` with `{ module: 'people', operation: 'read' }`: the tenant must hold a People entitlement with read access (including a cancelled entitlement inside `read_until`), and the member role must hold `people.read`. The response is a streamed RFC 4180 CSV of seven directory identity fields — `person_id`, `employee_code`, `first_name`, `last_name`, `display_name`, `work_email`, `phone` — for every non-deleted person the session member can see, ordered by `employee_code nulls last, id`. Tenant scope comes from `app.tenant_id` and RLS, and since 0012 the member's People scope narrows the same way it narrows `GET /v1/people`, because the export transaction also sets `app.user_id`; nothing is ever scoped from a caller value, and `tenant_id` query parameters and `x-tenant-id` are ignored.

The runtime role has column-level `SELECT` on exactly those seven fields plus `deleted_at`, which is used only to exclude soft-deleted rows and is never exported. It has no table-level `SELECT` on `person`, and every person column outside the directory identity and the two placement ids — including personal email, date of birth, gender, status, designation, employment type, `location_id`, `manager_person_id` and the timestamps — remains owner-only; `user_id` and `deleted_at` stay unwritable. The export itself is unchanged by the placement work: it still emits seven columns, so a legal entity name appears on the directory screen and not in the CSV. Since the write path the same role also holds `INSERT` on the eight columns a create names (`id`, `tenant_id` and the six identity fields) and `UPDATE` on the six identity fields plus the two placement columns, which is 10 `SELECT` + 8 `INSERT` + 8 `UPDATE` column privileges in all; `deleted_at` stays read-only, no placement column is insertable, there is still no table-level DML and no `DELETE`. The placement work added a separate column-only `SELECT` on `legal_entity (id, name, code, deleted_at)` and `org_unit (id, name, legal_entity_id, deleted_at)`, which the directory join and the placement options use — not the export — and neither table has a table-level grant or any write privilege. See the write path and placement sections above and [ADR 0008](suite/docs/adr/0008-people-write-path.md), [ADR 0009](suite/docs/adr/0009-people-placement.md). The route declares a server-side cursor and fetches batches of at most 1,000 rows (default 200), honours response backpressure, and rolls back the read transaction if the client disconnects. Before the first CSV byte is sent, a separate member transaction commits a `people.directory.exported` audit row with the tenant, actor, request IP and user agent; metadata is limited to module, format and the seven column names, with no row count or row data. A failure to write that audit row returns a sanitized 500 and no CSV. Fields are minimally quoted with doubled quotes and CRLF line endings; a value whose first character is `=`, `+`, `-`, `@`, tab or carriage return is prefixed with a single quote before quoting to reduce spreadsheet formula injection.

This is a scoped directory export, not the complete export and portability feature. There is no dedicated export permission (M1), export rate limit, UI or download button, filter, column selection or date range, Client or Work export, asynchronous or background export, signed URL, storage bucket or export history, and no full-suite export/re-import. M0 has not exited.

## Layout

```
apps/api      Fastify HTTP surface
apps/worker   PostgreSQL outbox worker
apps/web      React + Vite client
packages/db   pg client, migration runner, repositories, SQL
packages/contracts  shared DTOs and Zod schemas
packages/testkit    disposable local databases and test fixtures
```

Import boundaries: `web -> contracts`, `api -> db + contracts`, `worker -> db + contracts`, `db -> contracts`, `testkit -> db + contracts`. Production code never imports `testkit`; apps never import each other. Rules live in [eslint.config.js](eslint.config.js).
